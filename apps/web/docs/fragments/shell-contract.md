# 작업 공간의 틀: 서버의 계약에 관해 가정했거나 물어야 할 것 (조각 문서)

작성: 2026-11-10 23:40 KST. 틀(`src/lib/features/shell/`)을 만들면서 저장소(`lib/state`)의 메서드만 썼고, 서버의 API 모양은 새로 지어내지 않았다. 아래는 설계 문서에 답이 없어 **지금의 저장소와 메모리 구현이 하는 대로 따른 것**과, 계약이 나오면 확인할 것이다.

| #   | 무엇                                           | 지금 화면이 하는 것                                                                                                                                                                                             | 서버에 확인할 것                                                                                                                                           |
| --- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 보드를 카테고리의 어느 자리에 넣는가의 `index` | `Workspace.moveBoard(boardId, categoryId, index)`에 그 카테고리의 `boardIds`(옮기는 보드를 뺀 것)에서의 자리를 준다. 화면에 보이는 자리에서 옮겨 적는다(`sidebar-logic.ts`의 `filedIndex`)                      | `index`가 `boardIds`의 자리인가, 읽는 사람에게 보이는 보드만 센 자리인가. 뒤쪽이면 `filedIndex`를 빼고 화면의 자리를 그대로 보낸다                         |
| 2   | 지웠다 되살린 보드의 카테고리                  | 메모리 구현은 보드를 지울 때 모든 사람의 카테고리에서 그 보드를 빼고, 되살릴 때 도로 넣지 않는다. 화면은 지우기 전의 카테고리 목록을 들고 있어 그 자리에 다시 보이지만, 새로 읽으면 기본 카테고리의 끝으로 간다 | 되살린 보드가 원래 카테고리의 원래 자리로 돌아가는가. 지울 때 카테고리의 변경을 알리는가                                                                   |
| 3   | 새 보드의 첫 뷰                                | "보드 추가"가 `createBoard` 뒤에 `createView`를 따로 부른다. 요청이 둘이라 사이에 실패하면 뷰 없는 보드가 남고, 실행 취소 목록에 "뷰 만들기"가 한 칸 생긴다                                                     | 보드를 만들 때 첫 뷰를 함께 만드는 호출(또는 서버가 기본 뷰를 넣어 주는 것)이 있는가. 템플릿으로 만드는 호출은 범위 밖이라 보지 않았다                     |
| 4   | 열지 않은 보드에서의 내 역할                   | 보드 목록(`boards`)에는 역할이 없어, 사이드바는 열려 있는 보드에 대해서만 "보드 삭제"를 끌 수 있다. 다른 보드는 항목을 두고 서버의 403에 맡긴다                                                                 | 보드 목록에 읽는 사람의 역할(또는 "지울 수 있는가")을 실을 것인가. 보드를 지울 수 있는 역할은 무엇인가(관리자만인가)                                       |
| 5   | 기본 카테고리의 이름 바꾸기                    | 메뉴에 둔다. 메모리 구현은 받는다. 거절되면 저장소가 되돌리고 알린다                                                                                                                                            | 서버가 받는가. 받지 않으면 `SidebarList.svelte`의 `categoryActions`에서 그 줄을 뺀다                                                                       |
| 6   | 새 카테고리의 자리                             | 메모리 구현은 새 카테고리를 맨 위에 둔다(원본과 같다). 화면은 서버가 준 `sortOrder`를 따를 뿐이다                                                                                                               | 맨 위인가 맨 아래인가                                                                                                                                      |
| 7   | 카테고리의 순서 바꾸기                         | "위로"·"아래로"가 `reorderCategories`에 모든 카테고리의 id를 새 순서로 준다                                                                                                                                     | 한 칸 옮기는 데 전체 순서를 보내는 것이 맞는가(지금의 인터페이스가 그렇다)                                                                                 |
| 8   | 접은 사이드바, 개발용 표시, 언어               | 셋 다 기기에만 기억한다(`localStorage`의 `fvoci:sidebar`, `fvoci:dev`, `fvoci:locale`). 서버에 보내지 않는다. 화면 상태 주머니(`screenState`)는 쓰지 않았다                                                     | 없음(언어를 계정 설정에 넣기로 하면 `src/app/locale.ts`가 바뀐다)                                                                                          |
| 9   | 설정의 저장                                    | 항목 하나를 바꿀 때마다 `changeSettings`(= `patchSettings`)를 한 번 부른다. 시간대는 브라우저가 아는 IANA 이름이나 `auto`만 보낸다                                                                              | 브라우저와 서버의 시간대 목록이 다를 때(브라우저는 알고 서버는 모르는 이름) 서버는 400을 준다고 보고 있다. 그때 저장소가 되돌리고 알리는 것까지 테스트했다 |

메모리 구현에서만 되는 흉내를 화면에 붙인 것은 없다. 다만 `src/app/backend.ts`가 메모리 구현을 띄울 때 기기가 기억한 표시 설정을 씨앗에 넣는다(새로 고침 뒤에도 "어둡게"가 남게. 서버는 설정을 기억하므로 서버를 붙이면 그 세 줄은 필요 없다).
