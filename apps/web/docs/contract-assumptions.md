# 계약 없이 가정한 것 (서버 쪽에 넘기는 문서)

가정을 적은 때: 2026-11-10 23:10 KST – 2026-11-11 00:11 KST. 고쳐 쓴 때: 2026-11-11 02:46 KST. 고쳐 쓰면서 가정과 질문은 그대로 두고 글과 순서를 다듬었고, 계약이 나온 뒤 답이 난 것 넷을 붙였다.

웹앱(`apps/web`)은 서버의 계약(`contracts/openapi.json`)이 나오기 전에 화면을 끝까지 조립했다. 이 문서는 그러면서 서버의 설계 문서(저장소 루트의 `docs/s6-design.md`)에 **없어서 지어낸 곳**을 모은 것이다. 설계에 있는 것은 그대로 따랐고, 그것은 1절에 확인용으로만 적었다.

## 읽는 법

- **가정**은 지금 웹앱의 코드가 그렇게 돼 있다는 뜻이다. **질문**은 서버 쪽의 답이 필요한 것이다.
- "설계 1.2" 같은 번호는 저장소 루트의 `docs/s6-design.md`의 절 번호다.
- 항목의 번호(A1–G6, 6절의 번호)는 다른 문서와 코드의 주석이 그 번호로 부른다. 번호는 바뀌지 않는다.
- 경로는 따로 말하지 않으면 `apps/web` 기준이다. 서버의 계약 `contracts/openapi.json`과 설계 문서는 저장소 루트 기준이다.
- "원본"은 이 웹앱이 옮겨 온 출발점인 옛 웹앱이다. 원본과 견준 말은 7절에 모았다. 다른 절은 원본을 몰라도 읽힌다.

### 가정이 틀리면 고칠 곳

화면은 서버를 직접 부르지 않는다. 화면이 쓰는 읽기, 쓰기, 구독은 `src/lib/state/backend.ts`의 `Backend` 인터페이스 하나다. 지금은 메모리 구현(`src/lib/state/memory/`)이 꽂혀 있다. 서버를 부르는 구현을 만들면 `src/app/backend.ts`에서 바꿔 끼운다.

아래의 가정이 계약과 다르면 고칠 곳은 대부분 그 구현 하나다. 인터페이스의 모양까지 바뀌는 경우는 항목에 "인터페이스가 바뀐다"고 적었다.

## 2. 가정한 모양

번호는 이 문서 안의 것이다. 표에는 가정과 질문만 적었다. 왜 그렇게 가정했는지와 덧붙일 말은 표 아래에 같은 번호로 적었다.

### 카드

| #   | 가정                                                                                                  | 질문                                                                                                   |
| --- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| A1  | 카드 목록의 항목이 `hasBody`(불리언), `tasksTotal`, `tasksDone`(정수)을 싣는다                        | 멤버의 이름                                                                                            |
| A2  | 카드 패치는 `{title?, icon?, updatedProperties?, deletedProperties?}`이고 **속성 단위**로 합쳐진다    | 계약의 카드 패치가 속성 단위인가                                                                       |
| A3  | 본문 쓰기는 카드 패치와 **따로**인 호출이고 `{body, readAt}`를 보낸다                                 | 멤버의 이름. 카드 패치와 같은 라우트인가. 제목·속성 패치에도 읽은 판을 실어야 하는가                   |
| A4  | 409의 기준은 **카드의 `updateAt`**이다                                                                | **본문만의 판**(예: `bodyUpdateAt`)으로 비교하거나, 409의 답에 "본문이 달라졌는가"를 실어 줄 수 있는가 |
| A5  | 카드를 만들 때 `{title?, icon?, properties?, isTemplate?, body?}`를 보내고 서버가 카드(요약)를 답한다 | 만들면서 본문을 함께 실을 수 있는가                                                                    |
| A6  | 카드 복제는 화면이 한다. 카드를 읽고 같은 내용으로 새로 만든다                                        | 서버에 복제 라우트를 둘 것인가. **답: 계약에 있다**                                                    |
| A7  | 여러 블록을 한 번에 고치는 라우트가 **없다**고 봤다                                                   | 묶음 패치가 있는가. **답: 계약에 있다(`boards-and-blocks`)**                                           |
| A8  | "수정 시각" 정렬은 카드의 `updateAt`만 본다                                                           | 댓글이 카드의 `updateAt`을 올리는가. 아니면 목록에 `lastCommentAt` 같은 값을 실을 수 있는가            |

- **A1.** 설계 5.7은 "할 일 수와 본문이 있는지만 싣는다"고만 한다. 칸반 카드의 할 일 배지와 본문 표시가 이 값을 쓴다.
- **A2.** 속성 전체를 바꿔 쓰면 두 사람이 서로 다른 속성을 고칠 때 한쪽이 사라진다. 계약의 패치가 속성 단위가 아니면 화면은 "읽은 뒤 전체를 보내기"로 돌아가야 한다.
- **A3.** `readAt`은 쓰는 쪽이 읽은 카드의 `updateAt`이다. 설계 3.7은 "패치에 내가 읽은 `updateAt`을 싣고"라고만 한다. 지금 화면은 본문에만 읽은 판을 싣는다.
- **A4.** 설계가 그렇게 읽힌다. 이 기준이면 내가 속성 하나를 고친 직후의 본문 쓰기도 409가 된다. 지금은 화면이 409를 받으면 카드를 다시 읽고, 본문이 내가 알던 것과 같으면 새 판으로 **한 번 다시 보낸다**. 요청이 둘 더 든다.
- **A5.** 설계 3.2("ID는 서버가")의 연장이다. 복제와 카드 템플릿이 본문을 함께 싣는다.
- **A6.** 복제 라우트가 있는지 몰라서 화면이 하게 했다. 화면의 복제는 댓글과 첨부를 복사하지 않는다. 첨부까지 복사하려면 서버가 해야 한다.
- **A7.** 묶음 패치가 있는지 설계에 없었다. 그래서 카드 N장을 다른 열로 옮기면 뷰 패치 하나와 카드 패치 N개가 따로 간다. 실행 취소는 화면이 한 묶음으로 한다. 묶음 패치를 쓰면 드래그 한 번이 원자적으로 된다.
- **A8.** 카드 목록에 마지막 댓글의 시각이 없다.

- **B1.** 댓글은 카드별로 읽는다(`comments(cardId)`). 만들 때 문서를 보낸다. 댓글 고치기는 없다.

  3. 블록들: 바뀐 뒤의 전체. **카드는 본문 없는 요약으로** 온다.
  4. 블록 삭제: id들. 함께 지워진 아래 것까지 싣는다.
  5. 구성원: 전체 목록.
  6. 카테고리: 전체 목록.

## 3. 화면이 정한 처리 (서버의 답에 따라 달라질 수 있는 것)

- **낙관적 갱신.** 고치기는 화면에 먼저 보인다. 거절되면 되돌리고 알린다. 한 블록에 쓰기가 진행 중일 때 도착한 판(답과 메시지)은 붙들어 둔다. 마지막 쓰기가 돌아오면 가장 새 것을 적용한다(`src/lib/state/write.ts`).
- **409(본문).** 덮어쓰지 않는다. 카드를 다시 읽어, 저장된 본문이 내가 알던 것과 같으면 새 판으로 한 번 다시 보낸다. 다르면 두 글을 모두 들고 사용자에게 고르게 한다(`src/lib/state/card.svelte.ts`).
- **실행 취소.** 화면의 일이다. 고치기의 취소는 반대 패치를 보낸다. 만들기의 취소는 삭제이고, 삭제의 취소는 복원이다. 그래서 **복원 라우트는 휴지통에 있는 한 언제든 되어야 한다.** 만들기를 다시 실행하면 새 식별자의 것이 생긴다.
- **검색.** 열린 보드의 카드를 화면이 거른다. 찾는 곳은 제목과 속성이다. 목록에 본문이 없으므로 본문은 찾지 않는다. 본문 검색은 서버의 `body_text`(설계 5.7)가 생긴 뒤의 일이다.

웹앱 쪽에서 이 처리를 왜 골랐는지는 `docs/decisions.md`의 7–12번에 있다.

## 4. 본문의 허용 목록에 더하는 것 (편집기)

적은 때: 2026-11-10 23:52 KST. 편집기에 수식, 다이어그램, 이모지를 더하면서 서버의 검증·저장·계약이 맞춰야 하게 된 것만 적는다. 기준은 설계 5.7절의 허용 목록(`body_version` 1)이고, 거기서 **달라진 것만** 적는다. 웹앱 쪽의 구현은 `src/lib/editor/schema.ts`다. 허용 목록의 표 전체는 `docs/spike-editor.md` 2절에 있다.

### 4.1 한눈에

| 항목                | 내용                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `body_version`      | **1 → 2**                                                                                                                   |
| 새 노드             | `inlineMath`(인라인, 원자), `blockMath`(블록, 원자). 둘 다 속성은 `latex` 하나                                              |
| 바뀐 노드·마크·한도 | 없다. 깊이 32, 노드 20,000개, 직렬화 1 MiB 그대로. 새 노드도 노드 하나로 센다                                               |
| 다이어그램          | **허용 목록을 바꾸지 않는다.** 언어가 `mermaid`인 `codeBlock`이다. 서버는 언어를 보지 않는다(지금의 `language` 규칙 그대로) |
| 이모지              | 바뀐 것 없다. 글자(`text`)다                                                                                                |
| 판 1의 문서         | 그대로 판 2의 문서다(새 노드를 더했을 뿐 뺀 것이 없다). 옮길 것이 없다                                                      |

### 4.2 새 노드

| 노드         | 속성                                 | 안에 올 수 있는 것   | 어디에 올 수 있는가                                                                         |
| ------------ | ------------------------------------ | -------------------- | ------------------------------------------------------------------------------------------- |
| `inlineMath` | `latex`: 문자열, **1–4,000자, 필수** | 없음(`content` 없음) | 인라인 자리: `paragraph`, `heading` 안. `text`, `hardBreak`, `mention`과 같은 자리          |
| `blockMath`  | `latex`: 문자열, **1–4,000자, 필수** | 없음(`content` 없음) | 블록 자리: `doc`, `listItem`, `taskItem`, `blockquote` 안. `paragraph`, `image`와 같은 자리 |

- 블록 목록: `paragraph`, `heading`, `bulletList`, `orderedList`, `taskList`, `blockquote`, `codeBlock`, `horizontalRule`, `image`, **`blockMath`**.
- 인라인 목록: `text`, `hardBreak`, `mention`, **`inlineMath`**.
- `codeBlock` 안에는 여전히 `text`만 온다(`inlineMath`는 올 수 없다).
- `listItem`·`taskItem`의 첫 자식은 여전히 `paragraph`다(`blockMath`가 첫 자식일 수 없다).
- 다른 노드처럼 `marks`와 `text` 멤버를 가질 수 없다(`marks`는 `text` 노드에만).
- `latex` 밖의 속성은 거절한다.
- 그린 결과(HTML, MathML)는 저장하지 않는다. 저장하는 것은 **LaTeX 원문 문자열 하나**뿐이다.
- 이름은 편집기 라이브러리(Tiptap)의 공식 수식 확장이 쓰는 이름 그대로다(`inlineMath`, `blockMath`, 속성 `latex`).

예:

```json
{
  "type": "doc",
  "content": [
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "에너지는 " },
        { "type": "inlineMath", "attrs": { "latex": "E = mc^2" } },
        { "type": "text", "text": " 입니다." }
      ]
    },
    { "type": "blockMath", "attrs": { "latex": "\\int_0^1 x^2 \\, dx = \\frac{1}{3}" } },
    {
      "type": "codeBlock",
      "attrs": { "language": "mermaid" },
      "content": [{ "type": "text", "text": "flowchart LR\n  A --> B" }]
    }
  ]
}
```

#### `latex`의 한도: 무엇을 세는가 (맞춰야 할 것)

웹앱의 검증기는 문자열 길이를 **UTF-16 코드 단위**로 센다(JavaScript의 `length`). 이것은 `latex`만이 아니라 판 1의 모든 길이 한도(`fileId` 100, `alt` 1000, `userId` 100, `href` 2048, `language` 40)에 똑같다. 설계 5.7절은 "자"라고만 적었다. BMP 밖의 글자(이모지, 일부 한자)는 코드 단위 둘이다. 그래서 서버가 유니코드 스칼라 값으로 세면 경계에서 두 구현이 어긋난다.

- **요청**: 서버도 UTF-16 코드 단위로 세거나, 다르게 센다면 알려 달라(웹앱이 맞춘다). 어느 쪽이든 공유 테스트 벡터에 4.4의 "BMP 밖의 글자" 경우를 넣어 고정한다.
- `latex`의 내용은 검증하지 않는다(문법, 명령어, 제어 문자 모두). 어떤 문자열이든 길이만 맞으면 받는다. 틀린 수식은 그리는 쪽이 원문과 안내로 보여 준다. 서버가 LaTeX를 해석할 일은 없다.

### 4.3 서버가 뽑는 값

- **검색용 평문(`body_text`)**: 수식의 원문이 들어간다.
  - `inlineMath`는 그 줄 안의 그 자리에 원문 그대로 들어간다. 앞뒤에 아무것도 붙이지 않는다.
  - `blockMath`는 원문이 한 줄을 이룬다.
  - 다이어그램은 `codeBlock`이므로 지금 규칙대로 원문이 들어간다. 코드 블록의 글자가 한 줄이고, 안의 줄 바꿈은 그대로다.
  - 웹앱의 `plainText`로 4.2의 예를 뽑으면: `에너지는 E = mc^2 입니다.` / `\int_0^1 x^2 \, dx = \frac{1}{3}` / `flowchart LR⏎  A --> B` (줄마다 `\n`으로 잇는다. 빈 줄은 뺀다).
- **할 일 수**: 바뀐 것 없다(`taskItem`만 센다).
- **빈 본문 판정**: 바뀐 것 없다. 수식 하나만 있는 본문은 빈 본문이 아니다.
- **`file_refs`**: 바뀐 것 없다(수식과 다이어그램은 파일을 가리키지 않는다).

### 4.4 공유 테스트 벡터(`contracts/body-vectors.json`)에 더할 경우

받는 예:

1. 문단 안의 `inlineMath`(글자 사이, 문단의 처음, 문단의 끝, 문단에 그것 하나뿐).
2. `heading` 안의 `inlineMath`.
3. `doc` 바로 아래의 `blockMath`. `blockquote` 안, `listItem`의 둘째 자식, `taskItem`의 둘째 자식.
4. `latex` 1자. `latex` 4,000자(ASCII).
5. `latex`가 공백뿐인 문자열(`" "`), 줄 바꿈이 든 문자열, `<script>`처럼 마크업으로 보이는 문자열, `\href{javascript:…}{x}`: **모두 받는다**(내용은 보지 않는다).
6. BMP 밖의 글자: `"😀"`를 2,000번 이은 `latex`(UTF-16으로 4,000) → 받는다.
7. 언어가 `mermaid`인 `codeBlock`(평범한 코드 블록과 같게 받는다). 내용이 `%%{init: …}%%`이든 `click A href "javascript:…"`이든 받는다.

거절하는 예:

8. `latex`가 없는 `inlineMath`·`blockMath`(`attrs` 없음, `attrs: {}`).
9. `latex`가 빈 문자열. `latex` 4,001자. `latex`가 문자열이 아님(숫자, `null`, 배열, 객체, 불리언).
10. BMP 밖의 글자: `"😀"` 2,000번 + `"x"`(UTF-16으로 4,001) → 거절. 스칼라 값으로 세면 2,001이라 받게 된다. 이 벡터가 4.2의 "무엇을 세는가"를 고정한다.
11. 모르는 속성: `{"latex":"x","display":true}`, `{"latex":"x","html":"<span>x</span>"}`.
12. 자리: `doc` 바로 아래의 `inlineMath`. `paragraph` 안의 `blockMath`. `codeBlock` 안의 `inlineMath`. `listItem`의 첫 자식인 `blockMath`.
13. `content`가 있는 수식. `marks`가 있는 수식. `text` 멤버가 있는 수식.

평문 벡터(서버가 `body_text`를 벡터로 고정한다면): 4.3의 예 하나, `blockquote` 안의 `blockMath`, 수식만 있는 문단.

### 4.5 서버가 하지 않아도 되는 것, 그리고 알아 둘 것

- **수식과 다이어그램은 보는 사람의 브라우저에서 그린다.** 서버는 원문을 저장하고 돌려줄 뿐이다. 서버가 원문을 걸러 낼 필요는 없고, 걸러서도 안 된다. 공격 문자열도 글자로는 정당한 본문이다. 그리는 쪽의 방어는 `docs/spike-editor.md` 10절에 있다(KaTeX의 신뢰하지 않는 입력 설정, Mermaid의 엄격 설정과 그 뒤의 SVG 걸러 내기).
- **콘텐츠 보안 정책을 둔다면** 아래를 알아 둔다. 서버가 `index.html`에 붙이는 정책은 아직 없다.
  - `img-src 'self' data: blob:`와 `connect-src 'self'`를 권한다. 다이어그램 라이브러리에는 그리는 동안 주소의 그림을 불러오는 문법이 있다(노드를 그림으로 그리기). 웹앱은 그 문법을 원문 단계에서 막지만, 정책이 한 겹 더 막아 준다.
  - `style-src`에 `'unsafe-inline'`이 없어도 편집기와 수식은 동작한다. 스크립트가 넣는 스타일시트를 쓰지 않고, 인라인 스타일은 CSSOM으로만 준다.
  - 그때 **다이어그램은 색을 잃는다.** 그린 SVG 안의 `<style>` 요소가 막힌다. 웹앱이 그 스타일을 구성 가능한 스타일시트(`adoptedStyleSheets`)로 옮겨야 한다(`safe-svg.ts`의 한 곳). 정책을 정할 때 알려 달라.
  - `font-src 'self'`면 충분하다(KaTeX 글꼴은 앱의 `static/` 아래에서 온다).
  - 인라인 스크립트 하나를 해시로 허용해야 한다. 5절에 있다.
- **정적 파일**: 빌드 산출물에 `KaTeX_*.woff2` 20개가 더해진다. 해시가 든 이름이고, 이미 압축된 형식이라 `.br`·`.gz`를 만들지 않는다. 서버의 규칙(`has_content_hash`, `font/woff2`)은 그대로 맞는다.
- **고지**: 웹 고지(`static/THIRD_PARTY_NOTICES.txt`)에 KaTeX(MIT), KaTeX 글꼴(OFL-1.1), Mermaid와 그 의존성, CLDR 자료(Unicode-3.0)가 더해진다.
  - 루트 `deny.toml`의 허용 목록은 손대지 않았다. `OFL-1.1`은 여전히 그 목록에 없다(글꼴에 한해 웹 도구가 받는다).
  - ELK 레이아웃 엔진(`elkjs`, EPL-2.0 또는 GPL-3.0)은 번들에서 뺐다.

## 5. 그 밖에 넘길 것

### `index.html`과 콘텐츠 보안 정책

- `index.html` 머리에 인라인 스크립트가 하나 있다. 스타일시트가 그려지기 전에, 기기가 기억해 둔 밝기와 밀도를 루트 요소에 넣는다. 어두운 화면을 쓰는 사람이 밝은 화면을 잠깐 보지 않게 하려는 것이다.
- 정책이 인라인 스크립트를 막는다면(막아야 한다) 이 하나는 **해시로** 허용해야 한다.
- 빌드가 `dist/csp.json`에 `{"script-src": ["'sha256-…'"]}`를 쓴다(`tools/build/inline-scripts.ts`). 서버는 시작할 때 그 파일을 읽어, `index.html`과 함께 보내는 정책의 `script-src`에 더하면 된다.
- `{{.BaseURL}}` 치환은 그 스크립트의 글자를 건드리지 않는다. 스크립트 안에 그 자리 표시가 없다.
- `dist/csp.json`은 `static/` 밖에 있고 서빙 대상이 아니다.
- 웹앱의 미리 보기 서버는 정책의 한 안을 붙여서 돈다(`docs/decisions.md`의 40번). 종단 테스트가 그 정책 아래에서 위반 0건을 본다.

### base path와 화면의 주소

- **base path를 스크립트가 읽는 자리**는 `<meta name="fvoci:base" content="{{.BaseURL}}">`다. 라우터가 여기서 읽는다. 인라인 스크립트로 전역 변수를 심지 않는다. 서버가 `index.html`의 자리 표시를 전부 치환하므로 서버가 따로 할 일은 없다.
- **화면의 주소**는 `/board/<보드>/<뷰>/<카드>`(오른쪽부터 생략 가능)와 `/`다. 설계 2.3의 "그 밖의 GET은 `index.html`"에 들어간다. 로그인, 가입, 오류 화면의 주소는 아직 없다.

### 내장 템플릿의 산출물

서버가 내장 템플릿으로 받아 쓰는 것은 웹앱 쪽 변환기의 산출물 `tools/templates/output/`이다(설계 5.7절의 "3.10의 갱신"). 모양은 그 폴더의 `README.md`에 있다. 서버가 넣을 때 맞춰야 하는 것은 넷이다.

1. **온보딩 보드를 제목이 아니라 `onboarding` 표식으로 찾는다.** 서버의 `crates/server/src/app/templates.rs`는 제목 `Welcome to Boards!`로 찾는다(2026-11-10 20:09 KST에 본 것). 산출물에서는 그 제목이 `Welcome to fvoci!`로 바뀌었다.
2. **식별자는 넣을 때 새로 만든다.** 산출물의 식별자는 아카이브의 것이다.
3. **그림은 노드와 파일 목록만 싣는다.** 바이트는 원본 아카이브에 있다. "이미지를 뺄지"(설계 3.10의 추가 안)가 정해지면 산출물을 다시 만든다.
4. **`isTemplate`, 보드 종류, 판 번호는 서버가 넣을 때 정한다.**

## 6. 화면을 만들며 더 가정한 것과 물을 것

화면마다 따로 적은 것이다. 2절의 표와 겹치는 가정은 2절의 것이 기준이다. 어느 화면도 저장소(`lib/state`)에 있는 읽기와 쓰기만 썼고, 서버의 API 모양을 새로 지어내지 않았다. 아래는 그 저장소 위에서 화면이 기대는 것 가운데 설계에 답이 없는 것이다.

### 작업 공간의 틀

틀은 `src/lib/features/shell/`이다. 설계에 답이 없는 곳은 **지금의 저장소와 메모리 구현이 하는 대로** 따랐다.

1. **보드를 카테고리의 어느 자리에 넣는가의 `index`.**
   - 지금: `Workspace.moveBoard(boardId, categoryId, index)`에 그 카테고리의 `boardIds`(옮기는 보드를 뺀 것)에서의 자리를 준다. 화면에 보이는 자리에서 옮겨 적는다(`sidebar-logic.ts`의 `filedIndex`).
   - 질문: `index`가 `boardIds`의 자리인가, 읽는 사람에게 보이는 보드만 센 자리인가. 뒤쪽이면 `filedIndex`를 빼고 화면의 자리를 그대로 보낸다.
2. **지웠다 되살린 보드의 카테고리.**
   - 지금: 메모리 구현은 보드를 지울 때 모든 사람의 카테고리에서 그 보드를 뺀다. 되살릴 때 도로 넣지 않는다. 화면은 지우기 전의 카테고리 목록을 들고 있어 그 자리에 다시 보인다. 새로 읽으면 기본 카테고리의 끝으로 간다.
   - 질문: 되살린 보드가 원래 카테고리의 원래 자리로 돌아가는가. 지울 때 카테고리의 변경을 알리는가.
3. **새 보드의 첫 뷰.** (C1과 같은 질문이다.)
   - 지금: `Workspace.createBoard`가 보드를 만든 뒤(`Backend.createBoard`) 첫 뷰를 이어서 만든다(`Backend.createView`). 요청이 둘이라 사이에 실패하면 뷰 없는 보드가 남는다. 왜 이렇게 묶었는지는 `docs/decisions.md`의 45번에 있다.
   - 질문: 보드를 만들 때 첫 뷰를 함께 만드는 호출이 있는가. 또는 서버가 기본 뷰를 넣어 주는가. 템플릿으로 만드는 호출은 범위 밖이라 보지 않았다.
4. **열지 않은 보드에서의 내 역할.**
   - 지금: 보드 목록(`boards`)에는 역할이 없다. 사이드바는 열려 있는 보드에 대해서만 "보드 삭제"를 끌 수 있다. 다른 보드는 항목을 두고 서버의 403에 맡긴다.
   - 질문: 보드 목록에 읽는 사람의 역할(또는 "지울 수 있는가")을 실을 것인가. 보드를 지울 수 있는 역할은 무엇인가(관리자만인가).
5. **기본 카테고리의 이름 바꾸기.**
   - 지금: 메뉴에 둔다. 메모리 구현은 받는다. 거절되면 저장소가 되돌리고 알린다.
   - 질문: 서버가 받는가. 받지 않으면 `SidebarList.svelte`의 `categoryActions`에서 그 줄을 뺀다.
6. **새 카테고리의 자리.**
   - 지금: 메모리 구현은 새 카테고리를 맨 위에 둔다. 화면은 서버가 준 `sortOrder`를 따를 뿐이다.
   - 질문: 맨 위인가 맨 아래인가.
7. **카테고리의 순서 바꾸기.**
   - 지금: "위로"와 "아래로"가 `reorderCategories`에 모든 카테고리의 id를 새 순서로 준다.
   - 질문: 한 칸 옮기는 데 전체 순서를 보내는 것이 맞는가(지금의 인터페이스가 그렇다).
8. **접은 사이드바, 개발용 표시, 언어.**
   - 지금: 셋 다 기기에만 기억한다(`localStorage`의 `fvoci:sidebar`, `fvoci:dev`, `fvoci:locale`). 서버에 보내지 않는다. 화면 상태 주머니(`screenState`)는 쓰지 않았다.
   - 질문: 없다. 언어를 계정 설정에 넣기로 하면 `src/app/locale.ts`가 바뀐다.
9. **설정의 저장.**
   - 지금: 항목 하나를 바꿀 때마다 `changeSettings`(= `patchSettings`)를 한 번 부른다. 시간대는 브라우저가 아는 IANA 이름이나 `auto`만 보낸다.
   - 확인할 것: 브라우저는 알고 서버는 모르는 시간대 이름이면 서버가 400을 준다고 보고 있다. 그때 저장소가 되돌리고 알리는 것까지 테스트했다.

메모리 구현에서만 되는 흉내를 화면에 붙인 것은 없다. 다만 `src/app/backend.ts`가 메모리 구현을 띄울 때, 기기가 기억한 표시 설정을 씨앗에 넣는다. 새로 고친 뒤에도 "어둡게"가 남게 하려는 것이다. 서버는 설정을 기억하므로, 서버를 붙이면 그 세 줄은 필요 없다.

5. 필터를 고칠 때는 `filter` 전체를 보낸다. `filter-edit.ts`의 모든 함수가 손대지 않은 부분을 같은 객체로 둔다.

#### 서버 쪽에 물을 것

- 뷰의 `fields`를 서버가 검증하는가. 한다면 위의 가짜 id(`__title`, `__badges`), 빈 `groupById`, 빈 제목을 받아야 한다.
- 뷰의 수정 권한이 카드의 수정 권한과 따로인가. 지금 화면은 `board.canEdit` 하나로 가른다.

### 칸반과 갤러리

#### 묻는 것

1. **갤러리의 미리보기에 쓸 것을 카드 목록이 실어 줄 수 있는가.**
   - 갤러리 카드에 본문의 앞부분이나 첫 이미지를 보여 주려면 본문이 필요하다. 지금의 카드 목록(`Backend.cards`)에는 본문이 없고 `hasBody`, `tasksTotal`, `tasksDone`만 있다.
   - 갤러리가 카드마다 `Backend.card`를 따로 부르지 않게 했다. 그래서 미리보기와 대표 이미지는 그리지 않는다.
   - 필요하면 목록의 카드에 "첫 이미지의 파일 id"와 "본문 앞부분의 글자(예: 200자)" 같은 요약을 실어 주는 길이 있어야 한다.
   - 화면 쪽에서 그릴 자리는 `src/lib/components/card-face/CardFace.svelte`다.

#### 가정한 것

1. **선택지의 id는 클라이언트가 만든다.**
   - "+ 그룹 추가"는 `createId('block')`으로 만든 id의 선택지를 보드의 속성 정의에 더한다(`Backend.patchBoard`). 선택 속성의 편집기(`onCreateOption`)도 같은 가정을 한다.
   - 서버가 선택지의 id를 정한다면 `src/lib/features/views/kanban/board-data.ts`의 `addGroup`이 답에서 id를 읽게 바꿔야 한다. 그 id를 뷰의 `visibleOptionIds`에 넣는다.
2. **선택지를 지워도 서버는 카드의 값을 건드리지 않는다.**
   - 지운 선택지의 id를 값으로 가진 카드는 화면에서 값 없는 열에 보인다. 실행 취소(선택지를 정의에 되돌려 넣기)로 제 열에 돌아온다.
   - 서버가 선택지를 지울 때 카드의 값을 함께 지운다면 실행 취소로 돌아오지 않는다. 그때는 지우기 전에 묻는 글(`kanban_delete_group_description`)을 고쳐야 한다.
3. **뷰의 `visibleOptionIds`, `hiddenOptionIds`는 통째로 쓴다.** 열을 숨기고, 보이고, 순서를 바꾸는 일은 `BoardStore.setViewFields`로 두 목록을 새 값으로 바꾼다. 값 없는 열은 빈 문자열 id(`''`)로 목록에 든다.
4. **그룹 속성이 없는 보드 뷰.**
   - 뷰의 `groupById`가 비어 있으면 묶을 수 있는 첫 속성으로 묶어 그린다. 카드를 놓으면 그 속성의 값을 바꾼다. 뷰의 `groupById`를 채워 쓰지는 않는다.
   - 서버나 변환기가 보드 뷰에 `groupById`를 늘 채워 준다면 `BoardStore.groupingOf`의 대체 규칙은 쓰이지 않게 된다.

#### 저장소(`lib/state`)에 남기는 것

서버에 묻는 것이 아니라, 서버를 부르는 구현을 붙일 때 저장소 쪽에서 알아 둘 것이다.

- `BoardStore.dropCards`는 뷰의 순서를 쓰고 답을 기다린 뒤 카드의 속성을 쓴다. 그 사이에 화면은 카드가 떠난 열에 도로 선 것을 보게 된다. 그래서 칸반이 놓은 모습을 그 호출이 끝날 때까지 스스로 그린다(`Kanban.svelte`의 `settling`). 두 변경을 먼저 한꺼번에 보여 주고 나서 보내도록 저장소를 고치면 그 우회는 지워도 된다.
- 놓은 직후(쓰기가 끝나기 전)의 실행 취소는 이미 끝난 쓰기까지만 되돌린다. 종단 테스트는 쓰기가 끝난 뒤에 실행 취소한다(`data-settling`이 사라질 때까지 기다린다).

### 테이블

테이블 뷰가 쓰는 것은 모두 저장소에 이미 있는 것이다: 뷰의 `fields` 고치기(`setViewFields`), 카드의 속성·제목 고치기, 카드 만들기·복제·삭제, `dropCards`. 서버가 알아야 할 것은 뷰의 `fields`에 들어가는 값의 모양뿐이다.

| 필드                 | 테이블이 쓰는 값                                                                 |
| -------------------- | -------------------------------------------------------------------------------- |
| `columnWidths`       | 속성 id → 정수 px(100–800). 제목 열의 키는 `__title`                             |
| `columnCalculations` | 속성 id(제목 열은 `__title`) → 계산의 이름(주 1)                                 |
| `visiblePropertyIds` | 열의 순서. 숨기면 빠진다. 보드에 없는 속성의 id는 지우지 않고 뒤에 남긴다        |
| `sortOptions`        | 머리글 메뉴는 `[{propertyId, reversed}]` 하나로 갈아 쓴다. 제목 열은 `__title`   |
| `collapsedOptionIds` | 접은 그룹의 선택지 id. **값 없는 그룹을 접으면 빈 문자열 `''`이 들어간다**(주 2) |
| `cardOrder`          | 행을 끌면 `dropCards`가 보드의 모든 카드 id를 수동 순서로 다시 쓴다(주 3)        |

1. 계산의 이름은 `count`, `sum`, `countChecked`, `none` 등이다. `lib/logic/calculations.ts`의 `CALCULATION_IDS`와 `none`이 전부다.
2. 서버가 이 목록의 원소를 검사한다면 `''`를 받아야 한다. `visibleOptionIds`와 `hiddenOptionIds`에도 `''`가 들어간다.
3. 저장소의 동작이다. 테이블을 만들면서 바꾼 것이 아니다.

카드를 만들 때는 `properties`에 뷰의 필터가 요구하는 값과 그룹의 값을 담아 보낸다. 빈 값은 넣지 않는다.

1. 식별자를 만드는 함수는 `lib/logic/wire.ts`에 있다. 서버가 만든다면 "선택지를 만들고 곧 값으로 넣기"가 두 단계가 된다.
2. 화면은 실패한 쓰기마다 알림 줄을 띄울 뿐이다.
3. 그때는 서버가 `Content-Disposition`을 줘야 한다.

#### 물을 것

1. **보드와 여러 블록을 한 번에 고치는 쓰기가 있는가.** **답: 계약에 있다(`boards-and-blocks`).** 조작의 모양은 이 문서를 고쳐 쓸 때 보지 못했다.
   - 지금의 경계에는 묶음 쓰기가 없다. 속성의 종류 바꾸기는 `보드 1 + 고칠 뷰 수 + 값을 고칠 카드 수`번의 쓰기다. 뷰와 카드는 나란히 보낸다.
   - 카드가 수백 장인 보드에서는 느리고 중간 실패가 생긴다.
   - 물은 선택지는 셋이었다. (가) 서버가 묶음 쓰기를 준다. (나) 속성의 종류가 바뀔 때 서버가 값의 변환을 스스로 한다. (다) 지금대로 둔다.
2. **속성을 지우면 서버가 카드의 값과 뷰의 흔적을 정리하는가.** 정리한다면 화면이 뷰를 고치는 쓰기를 따로 보낼 필요가 없다. 실행 취소(속성을 되살리기)로 값이 돌아오는지도 서버에 달린다.
3. **종류와 맞지 않는 값을 서버가 검사하는가.** 예: 날짜 속성에 글자가 든 카드. 화면은 종류를 바꿀 때 새 종류가 읽지 못하는 값을 지운다. 그래도 다른 클라이언트가 남긴 값이 있을 수 있다. 검사한다면 언제(보드 패치 때, 카드 패치 때) 무엇으로 거절하는가.
4. **보드의 속성 정의의 순서.** 보드 패치는 고친 정의와 지운 식별자만 담고 순서를 담지 않는다. 지운 속성을 되살리면 맨 끝에 온다. 순서를 바꾸는 쓰기(또는 정의 목록 전체를 보내는 쓰기)가 있는가.
5. **남의 댓글을 지울 수 있는 사람.** 화면은 자기 댓글에만 삭제 단추를 보인다. 서버의 규칙이 정해지면 맞춘다.
6. **댓글만 달 수 있는 사람(commenter)과 첨부.** 화면은 첨부 올리기와 삭제를 편집 권한(`canEdit`)에 묶었다. 댓글 권한으로 파일을 올릴 수 있는가.
7. **떠나는 순간의 쓰기.** 탭을 닫거나 숨길 때 저장하지 않은 본문을 보낸다(`pagehide`, `visibilitychange`). 그 요청을 페이지가 사라진 뒤에도 끝까지 보내는지(`keepalive`)는 서버를 부르는 구현의 몫이다. 본문의 한도(1 MiB)가 `keepalive`의 한도(64 KiB)보다 크다는 점을 알려 둔다.

## 7. 원본과 견준 것

위의 가정 가운데 원본의 동작이나 모양에서 온 것, 원본과 일부러 다르게 한 것을 모았다. 포팅의 흔적을 걷어 낼 때 이 절만 떼어 내면 된다.

### 2절의 가정

| 항목   | 원본                                                                        |
| ------ | --------------------------------------------------------------------------- |
| A2     | 카드를 고칠 때 `fields.properties` 전체를 바꿔 썼다                         |
| A7     | 묶음 패치(boards-and-blocks)가 있었다. 그것이 남는지가 설계에 없어서 물었다 |
| A8     | "수정 시각" 정렬이 마지막 댓글의 시각까지 봤다                              |
| B1     | 원본에도 댓글 고치기는 없다                                                 |
| C2, C3 | 보드 패치의 모양과 뷰의 `fields`의 멤버는 원본의 것 그대로다                |
| C4     | 역할의 뜻은 원본 그대로다                                                   |
| E1     | 카테고리가 보드마다 `{boardID, hidden}`의 목록을 실었다                     |

| G2     | 변경을 100ms 동안 묶는 것과 id 중복 제거는 원본의 클라이언트가 하던 것이다  |

### 6절의 가정과 질문

- **작업 공간의 틀 6번.** 새 카테고리를 맨 위에 두는 것은 원본과 같다.
- **뷰 머리글.**
  - 빈 `groupById`는 원본의 "그룹 해제"가 쓰는 값이다.
  - 가짜 id `__title`, `__badges`는 원본의 상수다.
  - 원본은 새 표 뷰의 `columnWidths`를 `{"__title": 280}`으로 만들었다.
  - 필터를 고칠 때 `filter` 전체를 보내는 것, 빈 뷰 이름을 "(제목 없는 뷰)"로 보이는 것, 마지막 뷰의 삭제를 화면에서만 막는 것은 원본과 같다.
  - 원본은 뷰의 수정 권한과 카드의 수정 권한이 따로였다(뷰·속성을 고치는 권한과 카드를 만드는 권한).
- **칸반과 갤러리.**
  - 원본의 갤러리는 카드마다 본문의 앞부분이나 첫 이미지를 보여 준다. 이 앱의 갤러리는 그리지 않는다(묻는 것 1).
  - 선택지의 id를 클라이언트가 만드는 것(가정 1), 값 없는 열을 빈 문자열 id로 두는 것(가정 3), 그룹 속성이 없으면 묶을 수 있는 첫 속성으로 묶어 그리는 것(가정 4)은 원본과 같다.
- **카드 상세.**
  - 속성 정의와 선택지의 식별자를 클라이언트가 만드는 것(가정 1)은 원본과 같다.
  - 원본은 속성의 종류를 바꾸거나 지울 때 보드의 정의, 뷰들, 값이 있는 카드 전부를 요청 하나로 보냈다(질문 1).
  - 원본은 보드 관리자가 남의 댓글을 지울 수 있었다(질문 5).
