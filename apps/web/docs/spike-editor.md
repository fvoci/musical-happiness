# 편집기 스파이크 결과

작성 2026-11-10 18:40 KST. 갱신 2026-11-10 20:30 KST(읽기 전용 표시기: 9절을 더하고 6절의 끝과 8절의 한 행을 고쳤다). 웹앱 트랙(`fvoci/web`)에서 서버 트랙에 넘기는 문서다. 서버 쪽 설계 `docs/s6-design.md`(hafgufa 워크트리)의 3.7절 "본문을 트리로 저장할 때의 열과 서버 검증"과 3.10절 "내장 템플릿과 아카이브 형식"에 답한다. 시각은 모두 KST다.

## 결론

1. **본문을 Tiptap 트리(JSON)로 저장하는 기본안은 그대로 간다.** 3.7절의 B안(카드·댓글마다 문서 하나)에 맞는 편집기가 서고, 편집기가 내는 문서는 허용 목록 검증을 항상 통과한다.
2. **허용 목록은 3.7절의 목록에서 속성 하나만 더한다**: `orderedList`의 `start`. 노드 15종, 마크 5종의 이름은 그대로다. 정확한 속성과 포함 관계는 2절에 있다.
3. **내장 템플릿 13개는 손실 없이 변환된다.** 본문이 있는 카드 58장, 콘텐츠 블록 219개가 문서 58개가 됐고, 바뀌거나 사라진 구문은 0건이다. 다만 아카이브 자체에 원본 화면에서도 보이지 않는 블록 38개와 끊어진 참조 42개가 있다(3절).
4. **문서는 작다.** 템플릿 기준 중앙값 940바이트, 최대 2,100바이트다. 마크다운 원문의 약 6배지만 절대 크기가 작다. 본문 한도는 **직렬화한 JSON 1 MiB**를 권한다(5절).
5. **편집기의 번들 비용은 brotli 121 KB**(gzip 146 KB)다. 지금 앱 껍데기(12 KB)의 열 배라서, 카드를 열 때 따로 받는 조각으로 둔다(6절).
6. **읽기만 하는 화면은 편집기 없이 그린다.** 문서를 바로 DOM으로 그리는 표시기를 만들었고(검증기 포함 brotli 2.7 KB), 템플릿의 문서 58개와 손으로 만든 문서에서 편집기가 그린 것과 같다(9절, 2026-11-10 20:30 KST에 더함). 5번의 편집기 수치는 다시 재면 brotli 110 KB다(9절 "번들 크기").

### 마크

| 마크                       | 속성                   | 메모                                                                      |
| -------------------------- | ---------------------- | ------------------------------------------------------------------------- |
| `bold`, `italic`, `strike` | 없음                   |                                                                           |
| `code`                     | 없음                   | 편집기는 `code`를 다른 마크와 함께 쓰지 않는다. 서버가 강제할 필요는 없다 |
| `link`                     | `href`: 1–2048자, 필수 | 아래 규칙. `target`, `rel`, `title`은 저장하지 않는다(그릴 때 붙인다)     |

`href` 규칙(`schema.ts`의 `isAllowedHref`, 서버도 같게): 공백과 제어 문자(U+0000–U+0020, U+007F)를 모두 지운 뒤 판단한다. 스킴이 있으면 `http`, `https`, `mailto`만(대소문자 무관). 스킴이 없으면 앱 안의 경로로 보되 `//`로 시작하거나 역슬래시가 들어 있으면 거절한다(브라우저가 바깥 주소로 읽는다). 제어 문자를 지우는 이유는 브라우저가 스킴을 읽기 전에 탭·줄바꿈을 버려서 `java\tscript:`가 통하기 때문이다.

### 저장 형식의 규칙

편집기의 `getJSON()` 결과를 `toStoredDoc`이 한 번 정리해서 보낸다. 서버가 받는 모양은 다음과 같다.

- 노드는 `type`, `attrs`, `content`, `marks`, `text` 다섯 멤버만 갖는다. 그 밖의 멤버가 있으면 거절한다.
- **`null`은 없다.** 값이 없는 속성은 빼고, 속성이 하나도 없으면 `attrs` 자체를 뺀다(예: 언어 없는 코드 블록은 `{"type":"codeBlock","content":[…]}`).
- `marks`는 마크가 있을 때만 있다. 같은 종류가 두 번 올 수 없다. 순서에는 뜻이 없다(편집기는 스키마 순서로 낸다).
- 빈 본문은 `{"type":"doc","content":[{"type":"paragraph"}]}`이다. 권고: 클라이언트가 이것을 `body: null`로 보내고 서버는 NULL로 저장한다. 서버가 둘을 같게 다루기만 하면 된다.
- 한도: 깊이 32(`doc`이 1), 노드 20,000개. 목록 한 단계가 깊이 둘(`bulletList` → `listItem`)을 쓰므로 깊이 32는 목록 중첩 약 14단계다. 템플릿의 최대 깊이는 5다.

예:

```json
{
  "type": "doc",
  "content": [
    {
      "type": "heading",
      "attrs": { "level": 2 },
      "content": [{ "type": "text", "text": "할 일" }]
    },
    {
      "type": "taskList",
      "content": [
        {
          "type": "taskItem",
          "attrs": { "checked": true },
          "content": [{ "type": "paragraph", "content": [{ "type": "text", "text": "번역 검수" }] }]
        }
      ]
    },
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "담당 " },
        { "type": "mention", "attrs": { "userId": "…" } },
        { "type": "text", "text": " 문서는 " },
        {
          "type": "text",
          "text": "여기",
          "marks": [{ "type": "link", "attrs": { "href": "/board/…" } }]
        }
      ]
    },
    { "type": "image", "attrs": { "fileId": "…", "alt": "진행 그래프" } }
  ]
}
```

### 3.7절의 목록에서 더하거나 뺄 것

| 항목                                       | 판단                     | 이유                                                                                                                                                               |
| ------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `orderedList.start`                        | **더한다**               | 없으면 "3."에서 시작하는 목록이 1부터로 바뀐다. 템플릿에 번호 목록이 5개 있다(모두 1부터)                                                                          |
| 포함 관계와 "첫째는 문단"                  | **검증에 넣기를 권한다** | 종류와 속성만 보면 `paragraph` 안의 `heading` 같은 문서가 통과하고, 편집기가 그것을 읽을 때 말없이 고쳐 버린다. 그러면 저장된 것과 화면이 달라진다. 위 표가 전부다 |

| 이미지의 너비, 제목                        | 넣지 않는다              | 크기 조절 UI를 만들 때 `body_version`을 올려 더한다                                                                                                                |
| 이모지 노드                                | 넣지 않는다              | 이모지는 글자다. 자동 완성이 유니코드 문자를 넣는다                                                                                                                |
| 나란히 놓는 단(지금의 중첩 `contentOrder`) | 넣지 않는다              | 템플릿에 0건이다. 3.7절이 적은 "단 기능이 없으면 사라진다"는 손실은 템플릿에서는 생기지 않는다                                                                     |

### 서버 쪽에서 더 볼 것

- **`image.fileId`**: 그 파일이 같은 보드의 것인지(3.7절의 규칙 그대로). 붙여넣기로 남의 `data-file-id`가 든 HTML이 들어오면 편집기는 그 ID를 그대로 싣는다. 걸러 내는 곳은 서버다.
- **`mention.userId`**: 형식만 볼지, 그 보드의 멤버인지까지 볼지 정해야 한다. 편집기는 목록에서 고른 ID만 넣지만 붙여넣기로는 아무 ID나 들어올 수 있다. 화면은 모르는 ID를 ID 그대로 보여 준다.
- **검색**: 본문이 JSON이 되면 지금의 제목 검색처럼 문자열을 바로 찾을 수 없다. `schema.ts`의 `plainText`가 문서에서 글자만 뽑는다(문단마다 한 줄). 서버가 검색용 평문을 따로 둘지는 서버 쪽 판단이다.
- **카드의 할 일 수**: 원본은 마크다운의 체크박스와 checkbox 블록을 세어 카드에 배지를 붙인다. 이제 `taskItem` 노드를 세면 된다(`countTasks`). 클라이언트가 본문을 받아 세면 되므로 서버가 따로 줄 필요는 없다. 다만 목록 화면에서 본문 전체를 받지 않으려면 서버가 세어 주는 편이 낫다.

## 3. 내장 템플릿 13개의 변환

`server/assets/templates.boardarchive`를 읽어 카드마다 문서 하나로 바꿨다. 카드의 `contentOrder` 순서대로 text 블록의 마크다운은 `marked`(GFM, 줄바꿈은 줄바꿈 — 원본이 화면에 그릴 때와 같은 설정)로 읽어 노드로, image 블록은 `image`(`fileId`), 이웃한 checkbox 블록들은 `taskList` 하나로, divider 블록은 `horizontalRule`로.

### 아카이브 자체의 문제 (변환의 손실이 아니다)

- **주인 없는 콘텐츠 블록 38개.** 부모 카드가 아카이브에 없다(지워진 카드의 잔재). 템플릿 1에 6개, 2에 12개, 4에 7개, 7에 2개, 10에 3개, 12에 8개. 원본 화면에도 나오지 않는다. 변환에 넣지 않았다.
- **끊어진 참조 42개.** 카드의 `contentOrder`에 있는데 그 ID의 블록이 없다. 템플릿 10에 6개, 12에 3개, 13(온보딩)에 33개. 원본도 건너뛴다. 온보딩 보드는 카드 10장의 `contentOrder` 65개 가운데 33개가 비어 있는 셈인데, 원본에서 그 카드들이 어떻게 보이는지는 서버 쪽 스냅샷으로 확인하기를 권한다.
- 서버 설계 3.10절은 이미지 파일 14개라고 적었다. `contentOrder`에 걸린 image 블록은 15개, 아카이브의 image 블록은 16개다. 한 파일을 두 블록이 가리키거나 주인 없는 블록에 속한 것으로 보인다(확인하지 않았다).
- 카드 본문에 원본 제품의 이름이 7번 나온다. 바깥 주소로 가는 링크는 1개다(원본 회사의 문서 사이트). 3.10절의 결정대로 변환 때 처리할 대상이다.

### 일반적인 마크다운에서는 무엇이 바뀌나

템플릿에는 없지만 변환기가 다루는 경우다. `tests/editor/markdown.test.ts`가 고정한다. 변환기는 종류별 건수를 돌려준다(`notes`).

## 9. 읽기 전용 표시기

### 무엇을 만들었나

| 무엇                                                                                   | 어디                                                                                |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 그리는 함수 `renderBody`                                                               | `src/lib/editor/render.ts`                                                          |

공개 형태:

```ts
// src/lib/editor/render.ts
function renderBody(doc: unknown, options?: RenderBodyOptions): RenderedBody;

interface RenderBodyOptions {
  resolveUser?: (userId: string) => string | undefined; // 멘션의 이름. 없으면 ID를 보인다
  taskLabel?: (text: string, checked: boolean) => string; // 할 일 체크 상자의 접근성 이름
  document?: Document; // 노드를 만들 문서. 기본은 페이지의 것
}

type RenderedBody =
  | { ok: true; empty: boolean; fragment: DocumentFragment } // 본문의 블록들. `doc-body` 클래스의 요소 안에 넣는다
  | { ok: false; problems: string[] }; // 검증기가 말한 이유. DOM은 하나도 만들지 않았다
```

```svelte
<!-- src/lib/editor/BodyView.svelte -->
<BodyView {doc} {resolveUser} {taskLabel} class="p-4">
  {#snippet invalid(problems)}표시할 수 없는 본문{/snippet}
  {#snippet empty()}내용 없음{/snippet}
</BodyView>
```

- `doc`은 서버가 준 문서를 JSON에서 읽은 값이다. `null`과 없음은 빈 본문이고 오류가 아니다. 빈 본문의 저장 형식인 "빈 문단 하나"도 빈 본문으로 본다(`empty: true`, 그린 것 없음). 2절의 권고대로 둘을 같게 다룬다.
- 검증(`validateDoc`)에 실패하면 본문의 일부도 그리지 않는다. 무엇을 대신 보일지는 호출부가 정한다(부품에서는 `invalid` 스니펫).
- 부품은 `editor.css`를 스스로 가져오고, 그린 것을 `class="doc-body"`인 `<div>` 안에 넣는다. API나 상태 모듈에 기대지 않는다.
- 표시기와 그것이 가져오는 모듈에는 Tiptap, ProseMirror, marked가 없다. 가져오는 것은 `schema.ts`, `files.ts`, `drawing.ts`뿐이다. 글자는 텍스트 노드로, 속성은 `setAttribute`로만 넣는다. 문자열을 요소로 바꾸는 API(`innerHTML` 등 13가지)가 소스에 나오면 테스트가 실패한다.

그리는 방식에서 정한 것:

- **링크**: 편집기와 같은 `target="_blank"`, `rel="noopener noreferrer nofollow"`(이제 두 쪽이 `drawing.ts`의 한 상수를 쓴다). `href`는 그리는 자리에서 `isAllowedHref`를 다시 통과해야 속성이 된다. 통과하지 못하면 글자만 그린다.
- **이미지**: `src`는 `files.ts`의 `fileUrl(fileId)`. 주소를 풀 수 없으면 편집기처럼 `src` 없이 자리만 잡는다. `loading="lazy"`, `decoding="async"`. `alt`는 문서에 있을 때만 붙는다(편집기와 같다).
- **멘션**: 이름은 `resolveUser`가 준다. 모르면 편집기처럼 ID를 그대로 보인다.
- **할 일**: 진짜 체크 상자다. 상태(`checked`)가 그대로 읽히고, 누르거나 스페이스를 눌러도 바뀌지 않는다(클릭을 되돌린다). `disabled`로 두지 않은 것은 흐리게 그려져 편집기와 달라 보이기 때문이다. 바꿀 수 없다는 것은 `aria-readonly="true"`로 알린다. 접근성 이름은 그 할 일의 첫 문단의 글자이고 `taskLabel`로 문구를 바꾼다.
- **빈 줄**: 빈 문단·제목·코드 블록과, 줄바꿈이나 줄 바꿈 문자로 끝나는 문단에는 편집기와 같은 자리에 `<br>`을 둔다. 브라우저는 빈 마지막 줄에 높이를 주지 않으므로, 이것이 없으면 빈 문단이 사라지고 편집기와 높이가 달라진다.
- **마크의 겹침**: 저장된 마크의 순서에는 뜻이 없으므로 편집기의 순서(`link`, `bold`, `italic`, `strike`, `code`, 바깥부터)로 정렬하고, 이웃한 글자가 바깥쪽 마크를 공유하면 한 요소로 묶는다. 편집기가 그리는 방식 그대로다.

### 하면서 찾은 것 (표시기 밖)

- **편집기가 검증기가 거절하는 문서를 낼 수 있다.** 굵은 글자 안의 줄바꿈이나 멘션을 HTML로 읽으면(`<strong>a<br>b</strong>`) 편집기는 그 `hardBreak`와 `mention`에도 마크를 붙여 내보내고, 검증기는 "글자에만 마크가 온다"며 거절한다. 4절의 "편집기가 목록 밖의 것을 만들 수 있는가: 없다"는 이 경우에 맞지 않는다. 고치지 않았다(편집기의 동작과 허용 목록 가운데 어느 쪽을 바꿀지 정해야 한다). 표시기는 검증기를 따르므로 그런 문서를 그리지 않는다. 목록이 그것을 허용하게 되면 표시기는 이미 편집기와 같게 그린다(`tests/ui/body-render-unchecked.test.ts`의 마지막 테스트).
- **검증기가 객체라면 다 가진 이름을 목록에 있는 것으로 봤다.** `{"type":"constructor"}` 같은 마크가 통과했다(`MARK_SPECS[이름]`이 상속된 멤버를 찾는다). `Object.hasOwn`으로 고쳤다(`schema.ts` 두 줄, `tests/editor/schema-own-names.test.ts` 11건).
- **검증기는 문서 모양이 아닌 값에서 예외를 던진다.** `marks`가 숫자, `content`에 `null`, `attrs`가 숫자, 속성 이름이 `constructor`인 경우 등이다. 고치지 않았다. `renderBody`는 그 예외를 잡아 "그릴 수 없는 본문"으로 돌려준다. 검증기를 직접 부르는 다른 호출부는 같은 일을 해야 한다.

### 확인하지 못한 것

- **화면 낭독기.** 체크 상자의 상태와 `aria-readonly`, 이름이 실제로 어떻게 읽히는지 듣지 못했다. `aria-readonly`를 체크 상자에서 읽어 주지 않는 낭독기가 있을 수 있다.
- **Firefox, Safari, 실제 기기.** Chromium headless만 돌렸다. Firefox에서는 편집기가 경우에 따라 공백으로 끝나는 문단에도 `<br>`을 더한다(ProseMirror의 `requiresGeckoHackNode`). 모양에는 영향이 없을 것으로 보지만 비교하지 못했다.
- **한글 입력기로 넣은 글.** 브라우저 테스트는 글자를 직접 넣었다. 이 기기의 headless 브라우저에는 한글 글꼴이 없어 스크린숏의 한글이 빈 네모로 나온다(두 쪽이 같다).
- **아주 큰 문서를 그리는 시간.** 노드 한도(20,000개)의 문서가 그려지는 것만 확인했다.
- **Storybook 화면.** 빌드한 결과에서 네 이야기가 오류 없이 그려지는 것은 확인했다. 툴바의 테마·글자 크기 전환은 보지 않았다.
