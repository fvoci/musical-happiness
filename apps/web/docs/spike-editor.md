# 편집기 스파이크 결과

작성 2026-11-10 18:40 KST. 웹앱 트랙(`fvoci/web`)에서 서버 트랙에 넘기는 문서다. 서버 쪽 설계 `docs/s6-design.md`(hafgufa 워크트리)의 3.7절 "본문을 트리로 저장할 때의 열과 서버 검증"과 3.10절 "내장 템플릿과 아카이브 형식"에 답한다. 시각은 모두 KST다.

## 결론

1. **본문을 Tiptap 트리(JSON)로 저장하는 기본안은 그대로 간다.** 3.7절의 B안(카드·댓글마다 문서 하나)에 맞는 편집기가 서고, 편집기가 내는 문서는 허용 목록 검증을 항상 통과한다.
2. **허용 목록은 3.7절의 목록에서 속성 하나만 더한다**: `orderedList`의 `start`. 노드 15종, 마크 5종의 이름은 그대로다. 정확한 속성과 포함 관계는 2절에 있다.
3. **내장 템플릿 13개는 손실 없이 변환된다.** 본문이 있는 카드 58장, 콘텐츠 블록 219개가 문서 58개가 됐고, 바뀌거나 사라진 구문은 0건이다. 다만 아카이브 자체에 원본 화면에서도 보이지 않는 블록 38개와 끊어진 참조 42개가 있다(3절).
4. **문서는 작다.** 템플릿 기준 중앙값 940바이트, 최대 2,100바이트다. 마크다운 원문의 약 6배지만 절대 크기가 작다. 본문 한도는 **직렬화한 JSON 1 MiB**를 권한다(5절).
5. **편집기의 번들 비용은 brotli 121 KB**(gzip 146 KB)다. 지금 앱 껍데기(12 KB)의 열 배라서, 카드를 열 때 따로 받는 조각으로 둔다(6절).

### 마크

| 마크                       | 속성                   | 메모                                                                      |
| -------------------------- | ---------------------- | ------------------------------------------------------------------------- |
| `bold`, `italic`, `strike` | 없음                   |                                                                           |
| `code`                     | 없음                   | 편집기는 `code`를 다른 마크와 함께 쓰지 않는다. 서버가 강제할 필요는 없다 |
| `link`                     | `href`: 1–2048자, 필수 | 아래 규칙. `target`, `rel`, `title`은 저장하지 않는다(그릴 때 붙인다)     |

`href` 규칙(`schema.ts`의 `isAllowedHref`, 서버도 같게): 공백과 제어 문자(U+0000–U+0020, U+007F)를 모두 지운 뒤 판단한다. 스킴이 있으면 `http`, `https`, `mailto`만(대소문자 무관). 스킴이 없으면 앱 안의 경로로 보되 `//`로 시작하거나 역슬래시가 들어 있으면 거절한다(브라우저가 바깥 주소로 읽는다). 제어 문자를 지우는 이유는 브라우저가 스킴을 읽기 전에 탭·줄바꿈을 버려서 `java\tscript:`가 통하기 때문이다.

### 저장 형식의 규칙

편집기의 `getJSON()` 결과를 `toStoredDoc`이 한 번 정리해서 보낸다. 서버가 받는 모양은 다음과 같다.

- 노드는 `type`, `attrs`, `content`, `marks`, `text` 다섯 멤버만 갖는다. 그 밖의 멤버가 있으면 거절한다.
- **`null`은 없다.** 값이 없는 속성은 빼고, 속성이 하나도 없으면 `attrs` 자체를 뺀다(예: 언어 없는 코드 블록은 `{"type":"codeBlock","content":[…]}`).
- `marks`는 마크가 있을 때만 있다. 같은 종류가 두 번 올 수 없다. 순서에는 뜻이 없다(편집기는 스키마 순서로 낸다).
- 빈 본문은 `{"type":"doc","content":[{"type":"paragraph"}]}`이다. 권고: 클라이언트가 이것을 `body: null`로 보내고 서버는 NULL로 저장한다. 서버가 둘을 같게 다루기만 하면 된다.
- 한도: 깊이 32(`doc`이 1), 노드 20,000개. 목록 한 단계가 깊이 둘(`bulletList` → `listItem`)을 쓰므로 깊이 32는 목록 중첩 약 14단계다. 템플릿의 최대 깊이는 5다.

예:

```json
{
  "type": "doc",
  "content": [
    {
      "type": "heading",
      "attrs": { "level": 2 },
      "content": [{ "type": "text", "text": "할 일" }]
    },
    {
      "type": "taskList",
      "content": [
        {
          "type": "taskItem",
          "attrs": { "checked": true },
          "content": [{ "type": "paragraph", "content": [{ "type": "text", "text": "번역 검수" }] }]
        }
      ]
    },
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "담당 " },
        { "type": "mention", "attrs": { "userId": "…" } },
        { "type": "text", "text": " 문서는 " },
        {
          "type": "text",
          "text": "여기",
          "marks": [{ "type": "link", "attrs": { "href": "/board/…" } }]
        }
      ]
    },
    { "type": "image", "attrs": { "fileId": "…", "alt": "진행 그래프" } }
  ]
}
```

### 3.7절의 목록에서 더하거나 뺄 것

| 항목                                       | 판단                     | 이유                                                                                                                                                               |
| ------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `orderedList.start`                        | **더한다**               | 없으면 "3."에서 시작하는 목록이 1부터로 바뀐다. 템플릿에 번호 목록이 5개 있다(모두 1부터)                                                                          |
| 포함 관계와 "첫째는 문단"                  | **검증에 넣기를 권한다** | 종류와 속성만 보면 `paragraph` 안의 `heading` 같은 문서가 통과하고, 편집기가 그것을 읽을 때 말없이 고쳐 버린다. 그러면 저장된 것과 화면이 달라진다. 위 표가 전부다 |
| 표(`table`)                                | 넣지 않는다              | 템플릿에 0건. 확장 넷과 셀 병합·열 너비 속성이 딸려 온다. 필요해지면 `body_version` 2에서                                                                          |
| 밑줄, 형광펜, 글자색, 정렬                 | 넣지 않는다              | 원본에 없고 마크다운에도 없다                                                                                                                                      |
| 제목 4–6단계                               | 넣지 않는다              | 가져올 때 3단계로 낮춘다(템플릿에 0건)                                                                                                                             |
| 이미지의 너비, 제목                        | 넣지 않는다              | 크기 조절 UI를 만들 때 `body_version`을 올려 더한다                                                                                                                |
| 이모지 노드                                | 넣지 않는다              | 이모지는 글자다. 자동 완성이 유니코드 문자를 넣는다                                                                                                                |
| 나란히 놓는 단(지금의 중첩 `contentOrder`) | 넣지 않는다              | 템플릿에 0건이다. 3.7절이 적은 "단 기능이 없으면 사라진다"는 손실은 템플릿에서는 생기지 않는다                                                                     |

### 서버 쪽에서 더 볼 것

- **`image.fileId`**: 그 파일이 같은 보드의 것인지(3.7절의 규칙 그대로). 붙여넣기로 남의 `data-file-id`가 든 HTML이 들어오면 편집기는 그 ID를 그대로 싣는다. 걸러 내는 곳은 서버다.
- **`mention.userId`**: 형식만 볼지, 그 보드의 멤버인지까지 볼지 정해야 한다. 편집기는 목록에서 고른 ID만 넣지만 붙여넣기로는 아무 ID나 들어올 수 있다. 화면은 모르는 ID를 ID 그대로 보여 준다.
- **검색**: 본문이 JSON이 되면 지금의 제목 검색처럼 문자열을 바로 찾을 수 없다. `schema.ts`의 `plainText`가 문서에서 글자만 뽑는다(문단마다 한 줄). 서버가 검색용 평문을 따로 둘지는 서버 쪽 판단이다.
- **카드의 할 일 수**: 원본은 마크다운의 체크박스와 checkbox 블록을 세어 카드에 배지를 붙인다. 이제 `taskItem` 노드를 세면 된다(`countTasks`). 클라이언트가 본문을 받아 세면 되므로 서버가 따로 줄 필요는 없다. 다만 목록 화면에서 본문 전체를 받지 않으려면 서버가 세어 주는 편이 낫다.

## 3. 내장 템플릿 13개의 변환

`server/assets/templates.boardarchive`를 읽어 카드마다 문서 하나로 바꿨다. 카드의 `contentOrder` 순서대로 text 블록의 마크다운은 `marked`(GFM, 줄바꿈은 줄바꿈 — 원본이 화면에 그릴 때와 같은 설정)로 읽어 노드로, image 블록은 `image`(`fileId`), 이웃한 checkbox 블록들은 `taskList` 하나로, divider 블록은 `horizontalRule`로.

| ----------------------------------- | ----------------------------------------------- |
| 템플릿                              | 13                                              |
| 카드                                | 77                                              |
| 본문이 있는 카드(= 만들어진 문서)   | 58                                              |

| **바뀌거나 사라진 구문**            | **0종 0건**                                     |

"글자 대조"는 손실 집계와 따로 둔 검사다. text 블록마다 `marked`가 만든 HTML에서 태그를 걷어 낸 글자와 변환된 문서의 글자를 공백을 빼고 비교했다. 86개 모두 같다.

### 아카이브 자체의 문제 (변환의 손실이 아니다)

- **주인 없는 콘텐츠 블록 38개.** 부모 카드가 아카이브에 없다(지워진 카드의 잔재). 템플릿 1에 6개, 2에 12개, 4에 7개, 7에 2개, 10에 3개, 12에 8개. 원본 화면에도 나오지 않는다. 변환에 넣지 않았다.
- **끊어진 참조 42개.** 카드의 `contentOrder`에 있는데 그 ID의 블록이 없다. 템플릿 10에 6개, 12에 3개, 13(온보딩)에 33개. 원본도 건너뛴다. 온보딩 보드는 카드 10장의 `contentOrder` 65개 가운데 33개가 비어 있는 셈인데, 원본에서 그 카드들이 어떻게 보이는지는 서버 쪽 스냅샷으로 확인하기를 권한다.
- 서버 설계 3.10절은 이미지 파일 14개라고 적었다. `contentOrder`에 걸린 image 블록은 15개, 아카이브의 image 블록은 16개다. 한 파일을 두 블록이 가리키거나 주인 없는 블록에 속한 것으로 보인다(확인하지 않았다).
- 카드 본문에 원본 제품의 이름이 7번 나온다. 바깥 주소로 가는 링크는 1개다(원본 회사의 문서 사이트). 3.10절의 결정대로 변환 때 처리할 대상이다.

| `heading-level-clamped` | 4–6단계 제목은 3단계로                                                                                    |
| `table`                 | 표는 행마다 문단 하나로(칸은 `                                                                            | `로 잇는다) |

## 4. 확인한 동작

브라우저(Chromium headless, Playwright) 테스트 10종이 데스크톱과 터치 뷰포트에서 모두 통과했다(2026-11-10 18:36 KST, `20 passed (8.1s)`).

| 질문                                     | 결과                                                                                                                                                                                                                                                                                                |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 멘션 자동 완성                           | 된다. `@`를 치면 목록이 뜨고 화살표·Enter·Escape로 다룬다. 저장되는 것은 `{"type":"mention","attrs":{"userId":"…"}}`뿐이고 이름은 그릴 때 찾는다. 한글 이름(`@김`)으로 걸러진다                                                                                                                     |
| 이모지 자동 완성                         | 된다. `:rock`에서 🚀를 골라 넣는다. 들어가는 것은 유니코드 글자다. `10:30`이나 `http://`의 콜론은 목록을 열지 않는다                                                                                                                                                                                |
| 이미지가 `fileId`만으로 그려지는가       | 그려진다. 문서에는 `fileId`와 `alt`만 있고, `<img>`의 `src`는 그릴 때 `files.ts`의 한 함수가 만든다. 주소를 풀 수 없으면 `src` 없이 자리만 잡는다                                                                                                                                                   |
| 붙여넣기에서 목록 밖의 내용이 걸러지는가 | 걸러진다. `<script>`, `<iframe>`, `<style>`, `<object>`, 이벤트 속성, `style`, 밑줄, 표, 바깥 주소의 `<img>`, `javascript:`·`data:` 링크(문자 참조로 숨긴 `jav&#x61;script:` 포함), 링크의 `target`이 모두 사라지고 글자는 남는다. 붙여넣은 스크립트는 실행되지 않는다. 결과 문서는 검증을 통과한다 |
| 편집기가 목록 밖의 것을 만들 수 있는가   | 없다. 편집기 스키마의 노드·마크·속성 이름이 허용 목록과 정확히 같은지를 테스트가 비교한다(`tests/ui/editor.test.ts`). 검증기가 받아들인 문서는 편집기가 한 글자도 바꾸지 않고 읽는다                                                                                                                |
| 마크다운 입력 규칙                       | `# `, `- `, `1. `, `[ ] `, `**굵게**`, `` `코드` `` 등이 입력하면서 바뀐다                                                                                                                                                                                                                          |

걸러 내기는 ProseMirror의 방식 그대로다. 붙여넣은 HTML을 스키마의 해석 규칙으로 읽으므로 규칙이 없는 것은 문서에 들어오지 못한다. 별도의 새니타이저를 두지 않았다. 그래서 중요한 것이 "스키마가 허용 목록과 같다"는 테스트다.

## 5. 문서 크기와 본문 한도

템플릿의 문서 58개(직렬화한 JSON, UTF-8 바이트):

|               | 바이트 |
| ------------- | ------ |

| 90번째 백분위 | 2,072  |

- 같은 내용의 마크다운 원문은 중앙값 238바이트, 최대 928바이트다. 문서는 원문의 6.4배(중앙값)이고 가장 크게는 18.7배다. 짧은 항목이 많은 목록에서 배율이 크다(항목마다 `listItem` → `paragraph` → `text` 세 겹).
- 노드 수는 중앙값 22, 최대 44. 깊이는 최대 5.

합성 문서로 잰 큰 경우:

| 문서                                          | 노드   | 바이트  |
| --------------------------------------------- | ------ | ------- |
| 문단 100개 × 한글 80자                        | 201    | 29,926  |
| 문단 1,000개 × 한글 80자(8만 자, 긴 보고서)   | 2,001  | 299,026 |

| 빈 문단만으로 노드 한도 20,000                | 20,000 | 420,005 |
| 마크 붙은 한 글자 텍스트 노드로 채운 10,001개 | 10,001 | 954,026 |

**권고.**

- `body`의 직렬화 크기 한도: **1 MiB**. 8만 자짜리 문서의 세 배가 넘고, 노드 한도 20,000을 가장 비싼 모양으로 채운 것(약 1.9 MB로 추정)의 절반쯤에서 끊긴다. 노드 한도와 바이트 한도 가운데 먼저 닿는 쪽이 적용된다.
- 4.2절의 JSON 요청 한도 4 MiB는 그대로 충분하다. 카드 하나를 저장하는 요청은 본문 1 MiB + 속성이다.
- 4.2절이 적은 "블록의 `fields` 한도를 200,000자로 줄이는 안"은 타당해진다. 본문이 `body`로 나가면 `fields`에 큰 값이 들어갈 일이 없다.
- 4.1절의 "새 웹앱은 카드 저장 요청이 지금보다 커진다"에 대한 답: 템플릿 기준으로 카드 본문 하나가 0.4–2.1 KB다. 지금은 블록마다 요청이 따로 가고(블록 하나 중앙값 403 B) 이제는 본문 전체가 한 번에 간다. 글자 하나를 고쳐도 본문 전체를 보낸다.

## 7. 확인하지 못한 것

- **한글·일본어 입력기(IME).** 테스트는 글자를 직접 넣었고 조합 중인 입력은 거치지 않았다. 조합 중에 `@`나 `:` 목록, 입력 규칙이 어떻게 구는지는 실제 입력기로 봐야 한다.
- **Firefox, Safari, 실제 모바일 기기.** Chromium headless만 돌렸다. 터치 프로젝트는 뷰포트와 터치 플래그만 흉내 낸다.
- **화면 낭독기.** 자동 완성 목록에 `listbox`·`option` 역할은 붙였지만 읽히는지는 확인하지 않았다.
- **아주 큰 문서의 편집 속도.** 크기만 쟀다.
- **동시 편집.** 3.7절의 "읽은 `updateAt`을 싣고 다르면 409"는 서버가 생긴 뒤 W2 이후에 붙인다.
- **온보딩 보드의 끊어진 참조 33개**가 원본 화면에서 어떻게 보이는지.
