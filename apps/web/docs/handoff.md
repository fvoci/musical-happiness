### LAN 주소로는 Windows 밖에서 닿지 않는다

이 기기는 WSL2이고 네트워크 모드가 mirrored다(`wslinfo --networking-mode`). 확인한 것(2026-11-10 22:00 KST, 읽기만 했다):

| 어디서                    | 주소                         | 결과           |
| ------------------------- | ---------------------------- | -------------- |
| WSL 안                    | `http://192.168.0.15:18410/` | 200            |
| Windows(`curl.exe`)       | `http://localhost:18410/`    | 200            |
| Windows(`curl.exe`)       | `http://192.168.0.15:18410/` | 답이 없다      |
| 휴대폰 등 LAN의 다른 기기 |                              | 해 보지 못했다 |

지금까지 알아낸 원인: WSL의 Hyper-V 방화벽이 들어오는 연결을 기본으로 막는다(`Get-NetFirewallHyperVVMSetting`의 `DefaultInboundAction: Block`). LAN에 열린 규칙은 22번과 6768번 포트 둘뿐이고(`Get-NetFirewallHyperVRule`) 18410번의 규칙은 없다. 그래서 휴대폰에서는 닿지 않을 것으로 본다. Windows가 자기 LAN 주소로 건 연결이 답이 없는 것이 같은 이유인지, mirrored 모드에서 원래 그런 것인지는 가르지 못했다.

**방화벽과 Windows의 설정은 바꾸지 않았고, 바꾸지 않기로 했다**(사용자 결정). 휴대폰에서 터치 드래그와 한글 입력을 보는 방법은 정해지지 않았다.

## 걸렸던 함정

`PORTING.md`의 "이 기기에서 걸린 것"과 각 스파이크 문서의 "걸린 것"에 있는 것은 되풀이하지 않는다.

### 빌드와 서빙

- **스파이크의 빌드는 상대 주소를 써야 폴더 아래에서 서빙된다.** 처음에는 `/assets/…`로 나와서 `/screens/` 아래에서 스크립트가 404였다. HTTP 200만 보고는 몰랐고, 브라우저로 열어 실패한 요청을 세어 알았다. `vite.spikes.config.ts`의 `base: './'`.
- **`src/styles/app.css`가 `spikes/`를 Tailwind의 클래스 스캔에서 뺀다.** 스파이크마다 자기 CSS에서 `@source './*.svelte'`(파일 글롭)로 되살려야 한다. 편집기 스파이크는 그것이 없어서 배치 클래스가 생성되지 않고 있었다(`spikes/editor/spike.css`로 고쳤다).
- **글꼴 산출물은 커밋되지 않는다.** 새 워크트리는 `src/styles/fonts/`가 비어 있고, `build`가 다시 만들려면 원본 143 MB를 받는다. 이번에는 `target/fonts-snapshot/`에 사본을 두고 워크트리마다 복사했다. `tools/fonts/` 아래를 한 글자라도 고치면 스냅숏이 낡으므로 다시 떠야 한다(글꼴을 바꾼 뒤 한 번 다시 떴다).
- **스파이크와 Storybook이 앱의 글꼴을 싣게 하자 브라우저 테스트가 흔들렸다.** 글꼴은 늦게 도착하고(규칙은 브라우저가 한가할 때, 파일은 글자가 처음 필요할 때) 도착하면 줄이 바뀐다. 두 쪽을 차례로 재서 견주는 테스트는 그 사이에 걸린다. `editor/view.spec.ts`는 `networkidle`과 `document.fonts.ready`를 기다린 뒤, 재는 동안 아무것도 움직이지 않았는지까지 본다.

### 로직과 타입

- **`PropertyValue`가 넓어졌다**(날짜 값이 객체다). 글자나 목록을 기대하는 자리는 `plainPropertyValue`를 거친다. `String(값)`을 쓰면 린트(`no-base-to-string`)가 잡는다.
- **`Date.UTC`는 0–99년을 1900–1999년으로 읽는다.** 서버가 받는 연도는 1–9999라서 `dates.ts`가 `setUTCFullYear`로 만든다.
- **`formatDateValue`는 빈 값에 `undefined`를 준다.** 테스트에서는 `tests/logic/support/factory.ts`의 `storedDate`를 쓴다.
- **Tiptap(ProseMirror)의 `marks: ''`는 "이 노드 안에 올 수 있는 마크"다.** 노드 자신이 마크를 갖는지는 부모가 정한다. 줄바꿈에 마크가 붙지 않게 하려고 그 설정을 넣어 봤지만 효과가 없었다. 저장할 때 `toStoredDoc`이 글자가 아닌 노드의 마크를 뗀다.
- **검증기(`validateDoc`)는 어떤 값에도 예외를 던지지 않아야 한다.** 표시기의 비교 테스트가 던지는 경우들을 찾았다. 새 규칙을 더할 때 `tests/editor/schema.test.ts`의 "a value that is not shaped like a document"에 경우를 더한다.

### 문서와 커밋

- **문서에 시각을 미리 적지 않는다.** 일이 끝날 시각을 어림해 적었다가 여러 번 고쳤다. `date`를 찍고 그 값을 적는다.
- **이름 검사는 산출물도 본다.** 템플릿의 "바뀐 곳 목록"은 이전 문구에 원본의 이름이 들어가므로 `{old product name}`, `{old company name}`으로 가려서 쓴다(`tools/templates/rewrite.ts`의 `maskOldNames`).
- **생성물을 Prettier가 다시 접는다.** `JSON.stringify(…, null, 2)`의 배열 모양은 Prettier의 것과 다르다. 도구가 쓰는 파일은 `.prettierignore`에 넣고 "최신인가"는 테스트가 본다(`messages/`, `tools/templates/output/`).
- **체리픽한 뒤 생성물을 다시 만든다.** 두 작업이 `messages-own/`에 키를 더하고 `messages/`를 각자 생성했다. 합친 뒤 `pnpm --filter web run i18n:convert`와 `node tools/i18n/review.ts`를 돌려 차이가 없는지 봤다(이번에는 없었다).
- **측정 스크립트의 위치.** 번들 크기는 `target/scratch/measure.ts`(커밋되지 않음, 방법은 `docs/spike-editor.md` 9절), 테스트 매핑 표는 `target/scratch/from-agents/make-mapping.mjs`(에이전트의 워크트리에서 건져 둔 것)다. `target/`을 지우면 사라진다.

그동안 내가 직접 한 것: 날짜 와이어와 표시 설정, 글꼴, 템플릿 산출물, 정적 서버, 합치기와 검증, 창 크기에 관한 드래그·편집기의 확인.

나눈 방식:

- **공통 지시를 파일 하나에 두었다**(`target/agent-brief-common.md`, 커밋되지 않음): 기준 커밋으로 `reset --hard`하고 제목을 확인할 것, pnpm의 경로, 글꼴 사본, 금지 문자열, 건드리지 않는 파일, 닫힌 포트와 포트 번호, 프로세스를 죽이는 법, 커밋 메시지의 끝줄, 보고의 틀. 작업별 지시문은 그 파일을 먼저 읽으라고만 하고 그 작업의 것만 적었다.
- **파일의 주인을 지시문에서 나눴다.** `package.json`, `PORTING.md`, 잠금 파일, `tools/fonts/`, `app.css`는 아무도 건드리지 않게 했고(`app.css`만 속성 편집기가 색 토큰을 더했다), 작업마다 "네 파일"을 적었다. `messages-own/`은 속성 편집기만, 번역 작업은 새 폴더 `messages-override/`를 썼다. 충돌이 한 번도 없었던 것은 이 덕이다.
- **`PORTING.md`에 들어갈 것은 조각 문서로 받았다**(속성 편집기의 `docs/properties-test-mapping.md`). 합친 뒤 내가 `PORTING.md`에 이었다.
- **한 작업이 다른 작업의 결과를 써야 하면 먼저 그 접점만 커밋하고 그 커밋에서 시작하게 했다**(표시기가 템플릿 문서 58개를 읽을 수 있게 변환기를 라이브러리로 나눈 `17d04ad6`).
- **포트를 작업마다 주었다**(18331, 18341, 18351, 18361, 6016).
- **이어서 시킬 때는 같은 에이전트에게 보냈다.** 모바일 안의 중간 단계는 첫 판을 만든 에이전트가 문맥을 가지고 있어서, 새 기준 커밋으로 `reset --hard`하게 하고 요청을 그대로 옮겨 보냈다.

합칠 때의 주의점:

- **에이전트의 "통과"는 그 기준 커밋에서의 것이다.** 합친 뒤 `check`와 `test`를 다시 돌렸다. 합친 상태에서만 드러난 것이 있었다: 편집기 스파이크에 글꼴을 싣자 표시기의 브라우저 비교가 실패했다.
- **보고의 수치는 직접 뽑아 본다.** 보고와 실제가 어긋난 곳은 없었지만, 완료 조건을 확인하는 쪽은 보고가 아니라 이 세션의 출력을 요구했다. 종류별 이야기 수와 테스트 수, 드래그 결정 표의 행, 검수 표의 행과 원 표의 대응, 비교 테스트의 문서 수는 합친 뒤 다시 세었다.
- **"지시와 다른 점"과 "남긴 발견"을 읽는다.** 쓸모 있는 것이 거기에 있었다: 검증기가 예외를 던지는 경우와 줄바꿈의 마크(표시기), "Boards"는 5건이 아니라 4건이라는 것과 원 표가 44행이라는 것(번역), 기능 폴더끼리 가져올 수 없어 조립 방식을 정해야 한다는 것(속성 편집기), 넓은 화면의 가운데 대화상자가 접히는 자리에 걸린다는 것(모바일). 앞의 둘은 내가 이어서 고쳤다.
- **에이전트가 자기 보고에서 문서의 문장을 고쳐야 한다고 알려 오는 경우가 있다**("모두 열어 봤다"고 썼지만 실제로는 일부). 합치면서 고쳤다.
- **스크린샷처럼 환경에 달린 산출물은 합친 뒤 여기서 다시 만든다.** 글꼴이 바뀐 뒤 50장을 다시 찍었고, 두 번째 판의 64장은 여기서 다시 찍어 바이트가 같은 것을 확인했다.
- **사고 하나**(번역 에이전트의 보고): `target/` 아래에 푼 다른 커밋의 트리에서 `pnpm exec`를 부르자 pnpm이 심볼릭 링크를 타고 `apps/web/node_modules`에 잠금 파일 없이 설치했다. 지우고 `--frozen-lockfile`로 다시 설치했다. 추적되는 파일에는 영향이 없었다.
