## 1. 오류 응답 규칙

결정 대기 S6·S9·S11과 "보존한 quirk"의 대부분이 여기에 걸려 있다.

### 1.1 지금의 동작

- 본문은 `{"error": "<문구>", "errorCode": <상태 코드>}`. 문구는 원본의 것 그대로라 오타(`access denied to make board changesa`)와 내부 문구(`sql: no rows in result set`)가 나간다.
- 같은 종류의 잘못에 라우트마다 다른 상태 코드를 준다. 잘못된 JSON 본문이 400인 곳과 500인 곳이 섞여 있고, `null` 본문은 500이다. 이름이 이미 있는 가입, 시스템 카테고리 삭제, 개수가 안 맞는 재정렬, 없는 파일의 다운로드, 공유가 꺼진 설정에서의 공유 켜기가 모두 500이다.
- 없는 것과 권한 없는 것의 구분이 라우트마다 다르다. 묶음 패치는 없는 블록에 403, 카드 라우트는 없는 카드에 400, 콘텐츠 블록 이동은 누구에게나 404를 먼저 준다. 그래서 로그인한 사용자는 상태 코드로 ID의 존재 여부를 알 수 있다(S6, S9, S11).
- 모르는 API 경로와 메서드가 틀린 API 경로는 200과 `index.html`이다(2절).

### 1.2 본문의 모양

| 안 | 모양 | 장점 | 단점 |
|---|---|---|---|
| A. 그대로 | `{"error": 문구, "errorCode": 상태}` | 바꿀 것이 없다 | 화면이 문구로 분기해야 한다. 번역 키로 쓸 안정된 값이 없다 |
| **B. 코드 + 설명** | `{"error": "not_found", "message": "…", "reason"?, "field"?, "limit"?, "request_id"?}` | 화면이 `error`·`reason`으로 번역 문구를 고른다. GroundZero의 `ErrorBody`와 같아 웹 쪽 오류 처리 방식을 그대로 쓴다 | `error` 멤버의 뜻이 지금과 달라진다(문구 → 코드). 호환을 끝냈으므로 문제는 아니다 |
| C. RFC 9457 | `application/problem+json`, `{"type", "title", "status", "detail", …}` | 표준. 도구가 안다 | `type`에 넣을 문서 주소가 없어 `about:blank`와 확장 멤버를 쓰게 되고, 결국 B의 멤버를 다른 이름으로 싣는다 |

**권고: B.** 멤버의 뜻:

- `error` (필수): 오류의 종류. 상태 코드마다 하나인 닫힌 집합이다(1.3의 표).
- `message` (필수): 영어 설명. 로그와 개발자용이다. 화면에 그대로 쓰지 않고, 내부 세부(SQL 오류, 파일 경로)를 담지 않는다.
- `reason` (선택): 화면이 같은 종류 안에서 구분해야 할 때의 안정된 이유. 예: `invalid_credentials`, `signup_token_required`, `username_taken`, `last_admin`, `sharing_disabled`, `csrf`.
- `field` (선택): 거절된 입력 칸의 이름.
- `limit` (선택): 넘은 한도(4절).
- `request_id` (선택): 요청 로그의 같은 값. 500일 때 운영자가 로그에서 찾는 데 쓴다. 요청 ID를 로그와 응답 머리글(`x-request-id`)에 싣는 것이 함께 필요하다.

### 1.3 상태 코드

| 상태 | `error` | 언제 | 지금과 달라지는 것 |
|---|---|---|---|
| 400 | `bad_request` | 본문이 JSON이 아님, 타입이 틀림, `null` 본문, 검증 실패, 잘못된 쿼리 값 | 500이던 잘못된 본문 전부(로그인·가입·카테고리·공유·구독·boards-and-blocks·관리자), 패치의 잘못된 아이콘, 개수가 안 맞는 재정렬 |
| 401 | `unauthorized` | 세션이 없거나 끝남, 로그인 실패(`reason: invalid_credentials`) | 컴플라이언스 라우트의 401은 라우트와 함께 사라진다(1.6) |
| 403 | `forbidden` | 대상을 볼 수는 있는데 그 일을 할 권한이 없음(1.4). 헤더 검사 실패(`reason: csrf`), 가입 토큰이 없거나 틀림, single-user 모드에서 막힌 라우트 | 헤더 검사 실패는 지금 400, 가입 토큰 거절은 401 |
| 404 | `not_found` | 대상이 없음, 또는 요청자가 볼 수 없음(1.4). 모르는 API 경로(2절). 형식이 틀린 ID | 없는 카드의 400, 없는 블록의 403, 없는 파일 다운로드의 500, 공유 기록이 없을 때의 `sql: no rows…` |
| 405 | `method_not_allowed` | 아는 경로에 다른 메서드. `Allow` 머리글 포함 | 지금은 200과 `index.html` |
| 409 | `conflict` | 이미 있음(사용자 이름·이메일), 마지막 관리자를 빼려 함(`reason: last_admin`), 저장된 판과 요청의 판이 다름(3.7) | 이름이 이미 있는 가입은 지금 500, 마지막 관리자는 400 |
| 413 | `payload_too_large` | 본문이 한도를 넘음. `limit` 포함 | 4절 |
| 500 | `internal` | 서버의 잘못뿐. `message`는 고정 문구, 원인은 로그에만 | 위로 옮겨 간 것들이 빠진다 |

정하지 않고 두는 것: 422는 쓰지 않는다(검증 실패도 400. GroundZero와 같다). 501은 1.6에 따라 없어진다.

검사 순서는 모든 라우트에서 같게 한다: 세션(401) → 경로의 대상이 보이는가(404) → 그 일을 할 권한(403) → 본문 디코드와 검증(400) → 상태 충돌(409). 지금은 라우트마다 달라서, 비멤버가 400을 먼저 보는 곳이 있다.

### 1.4 권한이 없을 때 404로 답하는 범위

| 안 | 규칙 | 장점 | 단점 |
|---|---|---|---|
| A. 순서만 고침 | 권한 실패는 계속 403. 존재 확인보다 권한 확인을 먼저 해서, 없는 ID도 403 | 바뀌는 것이 가장 적다 | "없는 것에 403"이 된다. 지워진 보드의 링크를 연 멤버도 "권한 없음"을 본다. 멤버 여부를 알 수 없는 ID(카드 ID만 있는 `/cards/{id}`)에서는 어차피 조회가 먼저다 |
| **B. 보이는가로 나눔** | 요청자가 **볼 수 없는** 대상은 있든 없든 404. 볼 수는 있는데 그 일을 못 하면 403 | 존재 여부가 새지 않는다. 화면이 "찾을 수 없음"과 "권한이 부족함"을 구분해 안내할 수 있다 | 비공개 보드의 링크를 받은 비멤버는 "접근 거부"가 아니라 "찾을 수 없음"을 본다 |
| C. 전부 404 | 권한 실패는 모두 404 | 규칙이 한 줄 | viewer가 편집하려다 실패해도 "없음"이 된다. 화면이 이유를 말해 줄 수 없다 |

**권고: B.** "볼 수 있다"의 뜻을 대상별로 정하면 다음과 같다.

| 대상 | 볼 수 있는 요청자 | 볼 수 없으면 | 볼 수 있지만 권한이 없으면 |
|---|---|---|---|
| 비공개 보드와 그 블록·카드·멤버·공유 설정·파일 | 멤버. 읽기 토큰이 맞는 익명 요청(보드·블록·파일의 GET만) | 404 | 403 (예: viewer의 패치, editor의 멤버 관리) |
| 공개 보드 자체(조회, 참여) | 팀의 사용자 모두 | (해당 없음) | 403 (예: 비멤버의 편집) |
| 공개 보드의 내용(블록·카드·멤버·파일). 지금도 멤버만 읽는다 | 멤버. 읽기 토큰이 맞는 익명 요청 | 보드 경로로 부르면 403(보드가 있다는 것은 이미 보인다) | 403 |
| ID만으로 부르는 것(`/cards/{id}`, 구독의 블록, 콘텐츠 블록 이동의 두 블록) | 그 블록이 속한 보드의 내용을 읽을 수 있는 요청자 | 404 | 403 |
| 남의 카테고리 | 본인뿐 | 404 | (해당 없음) |
| 남의 구독 목록·사용자 설정 | 본인뿐 | 404 | (해당 없음) |
| 사용자 | 로그인한 사용자 모두 | (해당 없음) | 403 (남의 비밀번호 변경) |

- 익명 요청은 언제나 401이 먼저다. 401은 대상과 무관하게 나가므로 새는 것이 없다.
- 이 규칙으로 S6·S9·S11이 닫힌다. 권한 표의 스냅샷에서 비공개 보드의 `outsider` 열이 403에서 404로 바뀐다. 공개 보드의 `outsider` 열은 보드 경로의 라우트에서 403 그대로이고, ID만으로 부르는 라우트(`cards: get` 등)가 404로 바뀐다.
- **화면에 보이는 차이:** 비공개 보드 링크를 연 비멤버가 "찾을 수 없음" 화면을 본다. standalone에는 "접근 요청" 흐름이 없으므로 잃는 기능은 없다.

### 1.5 성공 응답

지금은 결과가 없는 작업이 `{}`, `null`, 그리고 `application/json`이라 표시된 맨 글자 `ok`로 제각각 답한다.

| 안 | 내용 | 장단점 |
|---|---|---|
| A. 200 + `{}`로 통일 | 모양만 맞춘다 | 바뀌는 것이 적다. 빈 객체를 읽는 의미 없는 디코드가 남는다 |
| **B. 204와 201** | 결과가 없으면 204(본문 없음), 새로 만든 것은 201과 그 객체, 그 밖은 200 | GroundZero와 같다. OpenAPI에서 응답이 분명해진다. 클라이언트가 204를 따로 다뤄야 한다 |

**권고: B.** 다만 1.2–1.4보다 급하지 않다. 따로 미뤄도 된다.

### 1.6 standalone이 거절만 하는 라우트

채널(`/teams/{team}/channels…`), 통계, 컴플라이언스(`/admin/boards…`), `GET /boards/{id}/metadata`, `/boards/search/linkable`은 501이나 401로 거절만 한다. 원본 웹앱이 부르기 때문에 남긴 것이다.

**권고: 지운다.** 새 웹앱은 부르지 않는다. 모르는 경로와 같은 404가 된다. `/users/me?channelID=`의 `permissions: ["create_post"]`와 보드·블록의 `channelId` 멤버도 함께 없앤다.

**결정: 지운다.** 구독의 `subscriberType: "channel"`도 함께 정리한다(받지 않는다). 저장 열(`boards.channel_id` 등)은 새 기준 스키마(3.1)에서 없어진다.

## 2. 경로 규칙과 끝 슬래시

### 2.1 지금의 동작

- 모르는 경로와, 아는 API 경로에 다른 메서드로 온 요청이 모두 200과 `index.html`이다.
- 끝 슬래시를 정규화하지 않는다. `/api/v2/boards/`는 모르는 경로로 떨어져 `index.html`이 된다.
- `/static`(슬래시 없음)과 `/static/` 아래의 없는 파일은 404다(본문은 `404 page not found`).
- axum 0.8은 끝 슬래시를 스스로 처리하지 않는다. 예전의 자동 리다이렉트는 없어졌고, `/foo` 라우트에 대한 `/foo/` 요청은 fallback으로 간다. 메서드가 틀리면 기본으로 405와 `Allow`를 답하는데, 지금은 원본을 따라 그것을 `index.html`로 덮어 두었다.

### 2.2 API의 끝 슬래시

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 404** | 정식 경로는 끝 슬래시 없는 형태 하나. 붙으면 모르는 경로 | 자원마다 주소가 하나다. 캐시·로그·프록시 규칙이 단순하다. 구현할 것이 없다(axum의 기본 동작) | 손으로 친 요청이 슬래시 하나로 404가 된다. `message`에 이유를 적어 준다 |
| B. 받아 준다 | 라우팅 전에 끝 슬래시를 잘라 낸다 | 관대하다 | 주소가 둘이 된다. 경로를 고쳐 쓰는 미들웨어는 라우터 전체를 감싸야 해서(axum 문서) 화면 경로와 base path에도 같이 적용된다 |
| C. 308 리다이렉트 | 슬래시 없는 주소로 보낸다 | 화면 주소에는 흔한 방식 | API에는 왕복이 한 번 늘 뿐이고, 본문 있는 요청의 리다이렉트를 따르지 않는 클라이언트가 있다 |

**권고: A.** 클라이언트는 OpenAPI에서 생성하므로 틀릴 일이 없다. GroundZero의 API 경로 172개에도 끝 슬래시가 없다.

### 2.3 규칙 전체

`{base}`는 base path다(없으면 빈 문자열). 설정에 끝 슬래시가 있든 없든 같은 결과가 나와야 하고, 테스트로 고정한다.

| 요청 | 응답 |
|---|---|
| `{base}/api/…`의 아는 경로, 맞는 메서드 | 핸들러 |
| `{base}/api/…`의 아는 경로, 다른 메서드 | 405 `method_not_allowed`, `Allow` 포함, JSON |
| `{base}/api/…`의 그 밖의 모든 것(끝 슬래시 포함, `{base}/api` 자체 포함) | 404 `not_found`, JSON. `index.html`을 주지 않는다 |
| 경로의 ID가 UUID 형식이 아님 | 404 `not_found`(있을 수 없는 ID는 없는 것이다. PostgreSQL의 `uuid` 열에 잘못된 값을 넘기지 않게도 된다) |
| `{base}/ws` | GET의 WebSocket 업그레이드만. 그 밖은 405 |
| `{base}/static/<파일>` | 있으면 파일, 없으면 404. 디렉터리 목록 없음(지금과 같다) |
| `{base}/static` | 404 |
| `{base}`와 `{base}/` | 200 `index.html`(리다이렉트하지 않는 예외) |
| 그 밖의 GET·HEAD, 끝 슬래시 있음 | 308, 슬래시 없는 같은 주소로. 쿼리 유지 |
| 그 밖의 GET·HEAD | 200 `index.html`(웹앱의 화면 경로) |
| 그 밖의 메서드 | 405, `Allow: GET, HEAD` |
| base path 밖의 모든 것 | 404(지금과 같다) |

헤더 검사(`X-Requested-With`)는 지금처럼 일치한 API 라우트에만 적용한다. 404와 405는 헤더와 무관하게 나간다.

### 2.4 이 문서에서 다루지 않는 것

경로 이름의 불규칙(`/teams/{team}/{board}/files`와 `/files/teams/{team}/{board}/{file}`, `block_ids`와 `boardIDs`의 표기 차이, 예약어가 아닌 `reorder`)은 OpenAPI를 내면서 한 번에 정리하는 편이 낫다. 여기서는 규칙만 정한다.

## 3. 새 기준 스키마

원칙: v40의 이력을 잇지 않고 **새 기준 하나**에서 시작한다. 옮겨 올 데이터가 없으므로 원본 서버가 만든 DB는 열지 않는다(시작할 때 알아보고 거절한다).

### 3.1 지금의 스키마에서 걷어 낼 것

- 쓰이지 않는 열과 테이블: `blocks.root_id`·`channel_id`, `boards.channel_id`, `categories.channel_id`, `sharing.workspace_id`, `subscriptions.workspace_id`, `board_members.roles`, `notification_hints` 테이블. `users.mfa_secret`·`auth_data`는 읽고 쓰기는 하지만 값을 쓰는 곳이 없다.
- 제약이 없는 곳: 사용자 이름·이메일에 유일 제약이 없어 동시 가입이 중복을 만든다. `file_info`에 기본 키가 없어 중복 행이 생길 수 있다. 외래 키가 하나도 없다.
- `preferences.category`: 값이 하나뿐이다(결정 1에서 `fvoci`로 확정). 열을 없애고 기본 키를 `(user_id, name)`으로 한다.
- 시각은 지금처럼 밀리초 정수(`BIGINT`)로 둔다. 와이어가 밀리초이고 두 DB에서 같은 SQL을 쓴다.

### 3.2 식별자: UUIDv7

- **만들기.** `uuid` 크레이트의 `Uuid::now_v7()`. 문서의 보장: "같은 프로세스가 이 메서드로 만든 UUID는 만든 순서대로 정렬된다." 프로세스 전체가 공유하는 문맥이 밀리초마다 무작위 값으로 다시 시작하는 42비트 카운터를 두고, 같은 밀리초 안에서는 카운터를 올린다. 시계가 뒤로 가면 마지막에 본 시각을 계속 쓴다. 문서가 보장하는 것은 단조 증가뿐이다.
- **보장하지 않는 것.** 프로세스가 둘이면(서버 여러 대, 재시작 전후) 서로의 순서는 시계에 달렸다. 그래서 ID 순서를 의미로 쓰지 않는다. 정렬은 계속 `create_at`으로 한다. ID가 시간순인 것은 색인의 삽입 지역성을 위한 것이다.
- **열 형식.** PostgreSQL은 `uuid`, SQLite는 하이픈이 든 소문자 36자 `TEXT`. SQLite에 16바이트 BLOB을 쓰면 색인이 작아지지만 두 DB의 SQL이 갈리고 도구에서 읽을 수 없다. 쓰지 않는다.
- **대상.** 팀, 보드, 블록, 사용자, 카테고리, 카테고리-보드 행, 세션의 `id`, 파일 정보.
- **종류 접두사.** 없앤다. 접두사에 기대는 코드는 한 곳이다: 파일 이름이 "접두사 한 글자 + 파일 정보 ID"라서 이름에서 첫 글자를 떼어 기록을 찾는다(`app/files.rs`, `store/blocks.rs`). 3.3에 따라 파일 이름이 ID와 무관한 난수가 되면서 이 규칙도 없어진다(파일 정보에 `name` 열로 찾는다).
- **ID는 서버가 만든다.** 블록 삽입과 boards-and-blocks 생성의 `id`는 지금도 그 요청 안에서 부모·자식을 잇는 임시 키로만 쓰이고 저장할 때 새로 만들어진다. 그렇게 문서화한다. 카테고리 생성처럼 요청의 `id`·`createAt`·`deleteAt`을 그대로 저장하는 곳은 받지 않게 바꾼다(있으면 400).

**팀.** standalone에는 팀이 하나(`0`)뿐이고, 같은 `0`이 내장 템플릿의 "전역 팀"으로도 쓰인다.

| 안 | 내용 | 장단점 |
|---|---|---|
| **A. 유지** | 팀 테이블과 `team_id` 열을 둔다. 루트 팀의 ID는 처음 시작할 때 만든 UUIDv7. 내장 템플릿은 팀 `0`이 아니라 보드의 표식 열(`builtin`)로 구분한다 | 계획(문서 7번)이 팀을 엔티티로 꼽는다. 와이어의 구조가 그대로다. 클라이언트가 팀 ID를 먼저 읽어야 한다(`GET /teams`) |
| B. 없앰 | `team_id`를 스키마와 경로에서 뺀다. 가입 토큰과 설정은 한 행짜리 인스턴스 테이블로 | 가장 단순하다. 지금 팀 권한 검사는 항상 참이다. 여러 팀을 다시 넣으려면 스키마와 경로를 다시 바꿔야 한다 |

**권고: A.** B가 더 단순하지만, 여러 팀을 쓸 계획이 없다고 확인되면 그때 B로 간다.

**결정: A.** 여러 팀을 쓸 계획이 있다. 그래서 지금은 항상 참인 팀 권한 검사(`permissions::has_permission_to_team`과 그것을 부르는 자리)를 지우지 않고 남긴다. 팀이 여럿이 될 때 그 자리에 실제 검사가 들어간다.

**ID가 생성 시각을 드러내는 문제.** UUIDv7의 앞 48비트는 만든 시각(밀리초)이다. 공개 공유(읽기 토큰)로 익명 요청자에게 나가는 것은 보드와 블록, 그리고 그 안의 `createdBy`·`modifiedBy`다.

- 보드와 블록의 ID: 응답에 `createAt`이 이미 들어 있다. 새로 드러나는 것이 없다.
- `createdBy`·`modifiedBy`의 사용자 ID: **그 사용자의 가입 시각**이 익명 요청자에게 드러난다. 새로 생기는 노출이다. 공유 화면은 세션이 없어 사용자 이름을 읽지 못하므로 이 두 값을 쓸 데가 없다.

**권고:** 읽기 토큰으로 답하는 응답에서 `createdBy`·`modifiedBy`를 뺀다.

### 3.3 비밀 값은 ID 생성기를 쓰지 않는다

세션 토큰, 공유 읽기 토큰, 가입 토큰, 저장 파일 이름은 운영체제의 난수 생성기에서 256비트를 받아 base64url 43자로 쓴다. 지금은 세션 토큰과 가입 토큰이 ID 생성기(`IdKind::Token`, 무작위 122비트)에서 나온다. UUIDv7으로 바꾸면 한 밀리초 안의 ID들은 카운터가 이어지고 무작위인 부분이 32비트뿐이라, 같은 생성기를 비밀 값에 쓰면 안 된다.

### 3.4 비밀번호: Argon2id

- **매개변수.** OWASP Password Storage Cheat Sheet의 Argon2id 최소 구성은 다섯 가지이고 서로 같은 방어 수준이라고 적혀 있다(차이는 CPU와 메모리의 교환): m=47104 t=1, **m=19456 t=2**, m=12288 t=3, m=9216 t=4, m=7168 t=5 (모두 p=1, m은 KiB). 문서 첫머리의 요약은 "19 MiB, 반복 2, 병렬 1"이다. `argon2` 크레이트 0.6.0의 기본값(`Params::DEFAULT`)이 바로 이 값이다.

  | 안 | 메모리 | 메모 |
  |---|---|---|
  | **m=19456, t=2, p=1** | 해시 하나에 19 MiB | OWASP 요약의 값이자 크레이트 기본값 |
  | m=47104, t=1, p=1 | 46 MiB | 메모리를 더 쓰고 CPU를 덜 쓴다 |
  | m=12288, t=3, p=1 | 12 MiB | 메모리가 작은 기기용 |

  **권고: m=19456, t=2, p=1.** 지금 비밀번호 작업은 프로세서 수만큼 동시에 돈다. 16코어면 최대 304 MiB를 쓴다. 동시 실행 수의 상한을 4로 두는 것을 함께 권한다(76 MiB).
- **저장.** PHC 문자열(`$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`)을 `users.password_hash`(TEXT)에.
- **다시 해시.** 로그인이 성공했을 때 저장된 매개변수가 현재 기준과 다르면 새로 해시해 저장한다. OWASP가 적은 방식이고, `argon2` 크레이트는 PHC 문자열에서 매개변수를 읽을 수 있다(`Params: TryFrom<&PasswordHash>`).
- **bcrypt.** 검증 경로를 남기지 않는다. 72바이트 제한과 그에 딸린 400도 사라진다.
- **길이.** 최소 8자(지금은 8바이트. 유니코드 스칼라 수로 센다), 최대 1,024바이트. 최대는 아주 긴 입력으로 해시 시간을 늘리는 것을 막는 값이고, 4.2의 인증 없는 라우트 한도(64 KiB) 안이다.
- **pepper.** 쓰지 않는다. OWASP는 "고려"로 적었고, 키를 설정에 두고 돌려 쓰는 부담이 생긴다.
- 블로킹 풀에서 실행하는 것은 그대로다.

### 3.5 저장 토큰의 해시

DB(또는 백업)를 읽기만 한 공격자가 살아 있는 서버에 들어오지 못하게 하는 것이 목적이다. 토큰이 256비트 난수이므로 느린 해시는 필요 없고 SHA-256이면 된다. 해시하면 다시 보여 줄 수 없다는 것이 값이다.

| 토큰 | 다시 보여 줘야 하나 | 안 | 권고 |
|---|---|---|---|
| 세션 | 아니다. 로그인 응답에 한 번 나간다 | 해시 저장 / 평문 | **해시.** `sessions.token_hash`에 유일 색인. 조회는 받은 토큰을 해시해서 |
| 가입 | 초대 링크를 다시 복사하려면 필요 | (a) 해시 + 만들 때 한 번만 보여 주고, 다시 필요하면 재발급(옛 링크는 죽는다) (b) 평문 저장, 관리자만 조회 | 권고는 (a)였다. **결정: (b).** 해시하면 두 번째 사람을 초대하려고 재발급할 때 첫 번째 사람의 아직 쓰지 않은 링크가 죽는다. 공유 토큰을 평문으로 두는 이유가 여기에도 그대로 적용된다 |
| 공유 읽기 | 공유 대화상자의 "링크 복사"가 매번 쓴다 | (a) 해시 + 한 번만 (b) 평문 저장 | **(b) 평문.** 토큰이 지키는 것(보드 내용)이 같은 DB에 있어 해시가 막아 주는 것이 "백업 이후에 바뀐 내용" 정도다. (a)는 링크를 다시 복사할 때마다 기존 링크가 죽는다 |

결정에 따라 계획의 "가입 토큰의 조회"는 그대로 된다(관리자만). 후속 후보로만 적어 둔다: 초대마다 토큰을 따로 두는 방식(초대 목록, 만료, 한 번만 쓰는 토큰). 그러면 토큰을 해시로 저장하면서도 한 사람의 초대를 다른 사람의 초대와 무관하게 무를 수 있다.

### 3.6 관리자 (S1, S2)

확정된 것(2026-11-10): 처음 가입한 사용자가 인스턴스 관리자다. 가입 토큰의 조회와 재발급은 관리자만 한다.

- **열.** `users.is_admin BOOLEAN NOT NULL DEFAULT false`. 역할이 둘뿐이라 enum 열은 두지 않는다.
- **첫 가입자.** "사용자가 0명이면 관리자"를 가입과 같은 트랜잭션에서 판정한다. 동시에 온 첫 가입 둘이 모두 관리자가 되지 않게, 한 행짜리 인스턴스 테이블의 `bootstrapped`를 조건부 갱신으로 바꾼 쪽만 관리자가 된다.
- **single-user 모드.** 가상 사용자가 관리자다.
- **최소 API.**
  - `GET /users/me`에 `isAdmin`.
  - `PUT /users/{id}/admin` `{"isAdmin": bool}`: 관리자만. 마지막 관리자는 해제할 수 없다(409 `last_admin`). 양도는 "상대를 지정하고 나를 해제"의 두 번이다.
  - `POST /teams/{team}/regenerate_signup_token`: 관리자만(지금은 누구나). 응답에 새 토큰.
  - `GET /teams/{team}`의 `signupToken`: 관리자에게만 넣는다(지금은 로그인한 누구에게나 나간다). 3.5의 결정에 따라 평문으로 저장하므로 다시 읽을 수 있다.
- **잠겼을 때.** 관리자 소켓에 "이 사용자를 관리자로" 명령을 하나 더 둔다. 관리자가 아무도 로그인할 수 없게 됐을 때의 복구 수단이다.
- 화면은 웹앱 트랙에서 다룬다.

### 3.7 본문을 트리로 저장할 때의 열과 서버 검증

계획의 기본안은 본문을 Tiptap 트리(JSON)로 저장하는 것이고, W3 전의 스파이크에서 확정한다. 여기서는 스키마가 그 결과를 받을 수 있는 모양을 정한다.

**어디에 두나.**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 지금처럼 블록 | 본문이 자식 블록들(text, image, divider, checkbox)이고 순서는 카드의 `contentOrder`. text 블록의 `title`이 마크다운 | 서버가 바뀌지 않는다 | 계획이 없애려는 마크다운 왕복이 남는다. 편집기가 블록 경계에 묶인다 |
| **B. 카드마다 문서 하나** | 카드 행(과 댓글 행)에 `body` 열. 이미지·체크박스·구분선은 문서 안의 노드 | 편집기의 문서가 그대로 저장 단위다. 본문을 한 번에 읽고 쓴다 | 콘텐츠 블록과 `contentOrder`, 콘텐츠 블록 이동 라우트가 없어진다. 나란히 놓는 배치(지금의 중첩 `contentOrder`)는 편집기의 단 기능이 없으면 사라진다 |
| C. 블록마다 조각 | 블록은 두고 text 블록이 트리 조각을 가진다 | 변화가 중간 | 두 구조의 단점을 함께 가진다 |

**권고: B.** 열:

- `blocks.body`: PostgreSQL `jsonb`, SQLite `TEXT`. NULL 가능(본문이 없는 블록).
- `blocks.body_version INT`: 허용 목록의 판. 목록을 넓힐 때 옛 문서를 알아보려고 둔다.
- 블록 테이블은 일반 저장소로 남긴다(카드·뷰·댓글을 종류별 테이블로 나누지 않는다). 나누면 스토어와 와이어 전체를 다시 짜야 하고, 그 값을 낼 요구가 아직 없다.

**서버 검증.** 검증 없이 받으면 다른 사용자의 화면에서 렌더링될 내용을 클라이언트가 마음대로 정한다. 허용 목록으로 "읽으면서 검증"한다: `fvoci-model`에 노드와 마크를 enum으로 두고, 모르는 종류나 속성이 있으면 디코드가 실패한다(400 `bad_request`, `field: body`).

- 노드: `doc`, `paragraph`, `heading`(level 1–3), `bulletList`, `orderedList`, `listItem`, `taskList`, `taskItem`(checked), `blockquote`, `codeBlock`(language), `horizontalRule`, `hardBreak`, `image`(fileId, alt), `mention`(userId), `text`.
- 마크: `bold`, `italic`, `strike`, `code`, `link`(href).
- `link`의 `href`는 서버에서도 스킴을 본다: `http`, `https`, `mailto`, 상대 경로만.
- `image`는 바깥 주소를 받지 않고 `fileId`만 받으며, 그 파일이 같은 보드의 것이어야 한다(S16의 규칙).
- 한도: 깊이 32, 노드 20,000개, 직렬화한 크기는 4.2의 블록 한도 안.
- 정확한 노드 집합은 스파이크에서 편집기 구성이 정해지면 그에 맞춘다. 위는 출발점이다.

**동시 편집.** 문서를 통째로 바꿔 쓰므로 두 탭이 서로를 덮어쓴다. 패치에 "내가 읽은 `updateAt`"을 싣고, 저장된 값과 다르면 409 `conflict`로 답하는 것을 권한다. 동시 공동 편집(CRDT)은 범위 밖이다.

### 3.8 서버가 만드는 공유 토큰 (S8)

지금은 토큰을 클라이언트가 정한다. 한 글자 토큰, 여러 보드에 같은 토큰, 빈 토큰이 저장된다.

- `POST /boards/{id}/sharing`의 본문은 `{"enabled": bool}`과 선택으로 `{"regenerate": true}`. `token`은 받지 않는다(있으면 400).
- 켤 때 토큰이 없으면 서버가 256비트 난수로 만든다. 응답과 `GET`은 `{"enabled", "token", "updateAt"}`(공유 권한이 있는 사용자에게만).
- 열: `sharing(board_id PK → boards, enabled, token UNIQUE, modified_by, update_at)`.
- 끌 때:

  | 안 | 내용 | 장단점 |
  |---|---|---|
  | **A. 토큰을 지운다** | 다시 켜면 새 링크 | 껐던 링크가 되살아나지 않는다. 끈 사람이 기대하는 것에 가깝다 |
  | B. 토큰을 둔다 | 다시 켜면 옛 링크가 다시 열린다 | 잠깐 껐다 켜도 링크가 유지된다. 한 번 새어 나간 링크를 죽이려면 `regenerate`를 따로 해야 한다 |

  **권고: A.**
- 공유가 꺼진 설정(`enablePublicSharedBoards: false`)에서의 `POST`는 403 `forbidden`, `reason: sharing_disabled`(지금은 500). 공유 기록이 없는 보드의 `GET`은 200 `{"enabled": false}`(지금은 404 `sql: no rows in result set`).

### 3.9 스키마 판과 마이그레이션

지금은 원본의 마이그레이션 기록 형식을 흉내 내어 "v40이 적용됨"을 써 두고, 테이블 이름에 접두사(`{p}`)를 끼워 넣는다. 접두사는 원본이 호스트 애플리케이션의 DB를 함께 쓰던 때의 것이다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. sqlx의 migrator** | DB 종류마다 디렉터리 하나(`schema/sqlite/0001_baseline.sql`, `schema/postgres/…`)를 바이너리에 넣는다. 기록은 `_sqlx_migrations` | 체크섬으로 고쳐 쓴 이력을 잡는다. 중간에 실패한 적용을 표시한다. PostgreSQL에서는 advisory lock으로 동시 실행을 막는다. 이미 쓰는 크레이트의 기능(`migrate`)이다 | SQL에 접두사를 끼워 넣을 수 없다. 접두사 설정을 없애야 한다 |
| B. 직접 만든다 | 기록 테이블과 적용 순서를 직접 구현 | 접두사를 유지할 수 있다 | 잠금, 체크섬, 실패 표시를 다시 만든다 |

**권고: A, 테이블 접두사는 없앤다.** 한 DB를 다른 것과 나눠 쓰려면 PostgreSQL의 스키마(`search_path`)를 쓴다. 테스트가 이미 그렇게 한다.

- 앞으로만 간다(되돌리는 마이그레이션은 두지 않는다).
- 시작할 때: 빈 DB면 기준을 적용한다. 더 새 판이 적용된 DB(옛 바이너리로 새 DB를 연 경우)와 원본 서버의 테이블(`db_migrations`, `schema_migrations`)이 있는 DB는 이유를 말하고 거절한다.
- 외래 키와 유일 제약을 넣는다: `board_members`·`sharing`·`blocks` → `boards`, `sessions`·`board_members`·`categories`·`preferences`·`subscriptions` → `users`, `lower(username)`과 `lower(email)`에 유일 색인, `file_info`에 기본 키와 `board_id`·`name` 열(S16의 "파일은 한 보드의 것"이 경로 문자열이 아니라 열이 된다).

### 3.10 내장 템플릿과 아카이브 형식

내장 템플릿 13개는 원본의 아카이브(`server/assets/templates.boardarchive`, 6.2 MB)를 그대로 바이너리에 넣고 시작할 때 가져온다. 본문과 링크에 원본 제품의 이름이 37번 나온다(회귀 테스트의 스냅샷에서 확인. 원본 회사의 문서 주소로 가는 링크가 대부분이다).

| 안 | 내용 | 장단점 |
|---|---|---|
| A. 그대로 | 옛 형식 가져오기를 유지 | 할 일이 없다. 옛 형식의 해석 코드, 마크다운 본문, 원본 이름이 남는다 |
| **B. 한 번 변환** | 템플릿을 새 스키마의 형식(트리 본문, UUID)으로 변환한 결과를 저장소에 두고, 옛 형식(v1 JSONL과 v2 ZIP) 가져오기 코드는 걷어 낸다. 변환할 때 원본 이름과 바깥 링크를 고쳐 쓰거나 뺀다 | 가져오기 코드가 새 형식 하나만 다룬다. 변환 스크립트는 한 번 쓰고 태그에 남긴다. 템플릿의 글을 누가 다시 쓸지 정해야 한다 |

**권고: B.** 3.7이 확정된 뒤에 한다. 아카이브의 새 형식(판 3)은 그때 함께 정한다. 사용자가 내보낸 옛 형식 아카이브를 가져올 일은 없다(옮겨 올 데이터가 없다).

**결정: B를 범위를 줄여서.**

- 바깥 링크와, 그 링크를 설명하는 문장은 뺀다(고쳐 쓰지 않는다).
- 원본 이름은 스크립트가 `fvoci`로 바꾼다.
- 변환 결과와 함께 **바뀐 곳의 목록**(보드, 블록, 바뀌기 전과 후)을 남긴다. 글의 검수는 사용자가 나중에 한다.

**추가 안(확인 필요): 이미지와 템플릿 수.** 아카이브 6.18 MB의 거의 전부가 파일 14개(압축 전 6.23 MB)다. 8개가 welcome 보드(온보딩 투어)의 것이고 6개가 다른 템플릿 4개의 것이다. 가장 큰 것이 1.19 MB짜리 GIF다. 서버 바이너리(릴리스 53 MB)의 약 12%다.

| 안 | 내용 | 장단점 |
|---|---|---|
| A. 그대로 넣는다 | 템플릿 13개와 이미지 14개를 지금처럼 바이너리에 넣고 시작할 때 저장소로 푼다 | 할 일이 없다. 바이너리와 첫 시작 시간(약 0.8초)이 그만큼 든다. 이미지는 원본 제품의 화면이라 새 웹앱의 모습과 맞지 않게 된다 |
| **B. 이미지를 뺀다** | 템플릿의 글과 구조만 넣는다. 이미지 블록 14개는 뺀다. 새 화면의 그림은 웹앱 트랙이 만들 때 다시 넣는다 | 바이너리가 약 6 MB 줄고 시작이 빨라진다. 원본 화면의 그림이 남지 않는다. 그림이 생길 때까지 welcome 보드는 글만 있다 |
| C. 템플릿도 줄인다 | B에 더해 13개를 5개 안팎으로 줄인다 | 검수할 글이 줄어든다. 무엇을 남길지는 제품 판단이다 |

**권고: B.** 그림은 원본 제품의 화면을 찍은 것이라 새 웹앱과 함께 어차피 다시 만들어야 한다. 템플릿 수(C)는 글을 검수할 때 함께 정하는 편이 낫다. 수치는 2026-11-10에 아카이브를 풀어 셌다(4.1).

## 4. 크기 한도와 스트리밍 (S5, S17, 의도적 차이 56)

### 4.1 잰 것

| 무엇을 | 값 |
|---|---|
| 원본 웹앱이 보낸 요청(원본 Cypress 스펙 6개의 흐름, 요청 922건 가운데 본문이 있는 206건) | 중앙값 77 B, 95번째 백분위 975 B, **최대 986 B** (`POST /boards-and-blocks`) |
| 내장 템플릿의 블록 379개(블록 하나의 JSON) | 중앙값 403 B, 99번째 백분위 1.8 KB, 최대 2.7 KB |
| 가장 큰 내장 템플릿 보드를 요청 하나(`POST /boards-and-blocks`)로 보낼 때 | 44 KB (블록 93개) |
| 내장 템플릿 아카이브 | 6.18 MB. 파일 14개가 6.23 MB이고 가장 큰 것이 1.19 MB(GIF). 압축은 거의 안 된다(풀면 6.48 MB) |
| 모델이 허용하는 블록 하나의 최대 | 제목 16,383자 + `fields` 800,000자. UTF-8로 한글이면 약 2.4 MB, 최악(4바이트 문자)은 약 3.3 MB |

한계: 요청 크기는 원본 웹앱의 것이다. 새 웹앱은 본문을 트리로 보내므로 카드 저장 요청이 지금보다 커진다. 그 크기는 스파이크에서 다시 잰다.

지금의 한도: JSON 본문은 제한이 없다(프레임워크의 기본 2 MB를 껐다). 업로드는 `maxfilesize`인데 기본값 0이 "제한 없음"이다. 가져오기는 요청 크기에 제한이 없고 항목 하나를 256 MiB까지 푼다(`board.jsonl`은 70 MB).

### 4.2 기본값 안

| 한도 | 설정 키(안) | 기본값(안) | 근거 |
|---|---|---|---|
| JSON 요청 본문 | `max_request_bytes` | **4 MiB** | 모델이 허용하는 가장 큰 블록 하나(3.3 MB)가 들어간다. 잰 최대(986 B)와 가장 큰 템플릿 보드(44 KB)의 약 90배 |
| 인증 없는 라우트(로그인, 가입)의 본문 | (고정) | **64 KiB** | 누구나 부를 수 있는 곳이다. 잰 최대 115 B |
| 업로드 파일 | `maxfilesize` | **100 MiB** (스트리밍을 하지 않기로 하면 25 MiB) | 잰 최대 1.19 MB. 첨부로 올 PDF와 짧은 영상을 넣을 수 있게. 스트리밍이면 메모리가 크기에 비례하지 않는다 |
| 가져오기: 아카이브(압축된 요청) | `max_import_bytes` | **256 MiB** | 잰 것 6.18 MB의 약 40배 |
| 가져오기: 풀린 합계 | (고정, 또는 위의 4배) | **1 GiB** | 압축 폭탄을 막는다. 템플릿은 압축률이 1.05배였다 |
| 가져오기: 항목 수 | (고정) | 10,000 | |
| 가져오기: `board.jsonl` 하나 | (고정) | 64 MiB | 지금 70 MB |
| 가져오기: 파일 항목 하나 | `maxfilesize`와 같다 | | 가져오기로 업로드 한도를 넘지 못하게 |
| WebSocket으로 받는 메시지 | (고정) | 64 KiB | 명령(AUTH, SUBSCRIBE)은 수백 바이트다 |

- 넘으면 413 `payload_too_large`와 `limit`. 가져오기의 오류가 200의 본문으로 나가는 것(보존한 quirk)도 표준 오류 응답이 된다.
- **0은 "제한 없음"이 아니게 한다.** 지금 `maxfilesize: 0`이 그 뜻인데, 실수로 무제한이 되기 쉽다. 값이 없으면 기본값, 0이나 음수면 시작 오류로 한다.

JSON 한도의 다른 안:

| 안 | 내용 | 장단점 |
|---|---|---|
| 2 MiB | 프레임워크의 기본값 | ASCII로 가득 찬 최대 블록(0.8 MB)은 들어가지만 한글로 찬 최대 블록(2.4 MB)이 413이 된다. 모델의 한도와 어긋난다 |
| **4 MiB** | | 모델이 허용하는 것은 모두 들어간다 |
| 1 MiB + 블록의 `fields` 한도를 200,000자로 | 한도를 함께 줄인다 | 본문이 `body` 열로 나가면(3.7) `fields`에 큰 값이 들어갈 일이 없어 타당해진다. 3.7이 확정된 뒤에 다시 볼 만하다 |

### 4.3 스트리밍 (의도적 차이 56)

지금은 업로드한 파일, 올린 아카이브 전체, 내보내는 ZIP 전체를 메모리에 올린다. 4.2의 한도(100 MiB, 256 MiB)를 그대로 두면 동시 요청 몇 개로 메모리가 기가바이트 단위로 든다.

| 경로 | 안 | 메모 |
|---|---|---|
| 업로드 | **요청 본문을 저장소로 바로 흘려 쓴다.** 흘리면서 크기를 세고, 넘으면 끊고 쓰던 것을 지운다 | 저장 계층의 쓰기는 이미 스트림을 받는다(`write(path, reader)`). 바꿀 곳은 API 계층이다 |
| 가져오기 | **요청을 디스크의 임시 파일로 받은 뒤**, 항목을 하나씩 읽어 저장소로 흘린다 | ZIP은 목차가 끝에 있어 임의 접근이 필요하다. 받으면서 풀 수 없다 |
| 내보내기 | **임시 파일에 ZIP을 쓴 뒤** 그 파일을 응답으로 흘린다 | `Content-Length`를 줄 수 있고, 중간에 실패해도 반쯤 나간 200이 생기지 않는다. 응답으로 바로 흘려 쓰는 방식은 실패를 상태 코드로 알릴 수 없다 |

- 임시 파일의 자리: 설정 `tmp_path`, 기본은 `filespath` 아래의 `.tmp`. 시스템 임시 디렉터리는 메모리(tmpfs)일 수 있어 기본으로 쓰지 않는다. 시작할 때 남은 임시 파일을 지운다.
- S3 백엔드에서도 임시 파일은 로컬 디스크에 둔다.

**권고: 바꾼다.** 하지 않기로 하면 업로드 한도의 기본값을 25 MiB로, 가져오기를 64 MiB로 낮추는 것을 권한다.

## 구현 순서(승인 뒤, 참고)

서로 기대는 순서만 적는다. 단계마다 스냅샷을 함께 고쳐 커밋한다.

1. 오류 본문과 상태 코드(1.2–1.4), 경로 규칙(2절). 보존한 quirk를 이 규칙에 맞춰 한꺼번에 정리한다. 스냅샷의 대부분이 여기서 바뀐다.
2. 크기 한도(4.2)와 스트리밍(4.3).
3. 새 기준 스키마: 마이그레이션 체계(3.9) → UUIDv7과 비밀 값(3.2, 3.3) → Argon2id와 토큰 해시(3.4, 3.5) → 관리자(3.6) → 공유 토큰(3.8). 회귀 테스트의 정규화가 UUID를 알아보게 고친다.
4. 본문 저장(3.7)과 템플릿 변환(3.10)은 편집기 스파이크 뒤.
5. OpenAPI를 내고 성공 응답(1.5)과 경로 이름(2.4)을 그때 정리한다.
